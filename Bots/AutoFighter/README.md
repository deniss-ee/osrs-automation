# AutoFighter

## Overview
AutoFighter fights weak, low-threat NPCs in a melee/ranged/magic combat loop with no banking or inventory management: find the nearest attackable NPC on screen, click it, wait for the fight to resolve (win or the click missed), repeat. It assumes the target NPCs are already aggressive/easy enough that no food/prayer/loot management is needed — it is the simplest bot in this framework (2 phases, no bank, no inventory step at all).

**Start location / setup assumptions**: the player must already be standing at the calibrated reference point (`refPointX/Y` in the `.ini`, currently `[1249, 702]` in screen coordinates — this is meant to represent the player/camera's fixed on-screen position, not a world position) with NPCs of the target color/overlay visible within `targetSearchRadiusX/Y` of that point. The camera/zoom/client window layout must match what was calibrated, since all coordinates are screen-absolute (`CoordMode` is set to `"Screen"` for Mouse/Pixel/ToolTip). RuneLite (or whatever window `WindowFocus` targets) must be the focused window before pressing F5, or every phase's focus guard will just idle in place. `runMode=1` in the `.ini` means every click is sent with Ctrl held (OSRS "force-run"/quick-action modifier) — verify this is the intended click behavior for the specific NPC/action being automated.

**Required calibration** (re-measure if resolution/client layout/zoom changes):
- `refPointX/Y` — the fixed screen point treated as "where the player is," used only to pick the *nearest* NPC blob when several are in view.
- `targetSearchRadiusX/Y` — half-width/half-height of the scan box around the ref point; must be sized to comfortably cover the NPC pen/area being fought in, without being so large it re-introduces the whole-screen performance cliff (see Known Risks).
- `targetColor`/`targetColorTolerance` — the NPC overlay color (`0xFF00FF` magenta, an OSRS NPC-highlight overlay, not the NPC's actual sprite color) and its match tolerance.
- `combatIndicatorX/Y` — the single fixed pixel used as the combat-state indicator (an HP-bar/overlay pixel), plus `combatStartColor`/`combatKillColor`, the two colors it takes while fighting vs. after a kill.
- All of the above are screen-absolute pixel coordinates/colors tied to one client window position, resolution, and zoom level — any of those changing invalidates every one of them.

## State Machine
Two phases, both defined as **shared, bot-agnostic classes** in `Core/SharedPhases.ahk` (not bot-specific despite ARCHITECTURE.md's older framing — see "Shared phases" note below). This bot only supplies construction parameters; see `ARCHITECTURE.md` for the general framework contract (`Phase.Run(ctx) -> nextPhaseName`, `Engine.Tick()`, `FailSafe` timeout semantics) and `Core/SharedPhases.ahk` itself for the two phases' full internal logic/comments.

| Phase | Class | Does | Returns next phase when |
|---|---|---|---|
| `scanAndAttack` | `ScanAndAttackPhase` | Scans a box (`refPointX/Y` ± `targetSearchRadiusX/Y`) for the nearest `targetColor` blob via `ColorSearch.FindNearestBlobCenter`, clicks its centroid. | On a successful find+click → `"waitCombat"` (constructed as this bot's `nextPhaseName`). On no match, polls (`scanPoll`) and stays `"scanAndAttack"` until `targetWaitTimeoutMs` elapses, then calls `ctx.engine.Stop(...)` and still returns `"scanAndAttack"` (the engine is stopped, so this return value is moot — see Known Risks). |
| `waitCombat` | `WaitCombatPhase` | Polls the fixed `combatIndicatorGate` pixel for `combatStartColor` (fighting) / `combatKillColor` (kill confirmed), with a stale-kill-color entry baseline guard. | Fresh kill confirmed → settles (`postKillSettle`) then returns `killNextPhaseName`, which this bot constructs as the **default** value `"scanAndAttack"` (see wiring below — AutoFighter has no loot step, unlike `AutoFighterLoot`). No signal at all past `retryClickAfterMs` → returns `retryNextPhaseName`, also defaulted to `"scanAndAttack"` for this bot, to retry the scan+click. No signal at all past `combatStartTimeoutMs` → `ctx.engine.Stop(...)`, stays `"waitCombat"` (return value moot, same as above). While `combatStartColor` matches → stays `"waitCombat"`, resetting the phase timer every tick (see below). |

**This bot's specific construction of the shared phases** (`Bots/AutoFighter/autofighter.ahk:100-111`):
```
botScanAndAttackPhase := ScanAndAttackPhase(
    targetColor, targetColorTolerance, refPointX, refPointY,
    targetSearchRadiusX, targetSearchRadiusY, targetBlobRadius,
    targetSampleRate, targetSeedRowStep, "scanPoll",
    targetWaitTimeoutMs, "waitCombat", runMode
)
botWaitCombatPhase := WaitCombatPhase(
    combatIndicatorGate, combatStartColor, combatKillColor,
    "combatPoll", retryClickAfterMs, combatStartTimeoutMs, "postKillSettle"
    ; killNextPhaseName and retryNextPhaseName both omitted -> both default to "scanAndAttack"
)
```
Loop: `F5` starts at `"scanAndAttack"`. Steady state is `scanAndAttack -> waitCombat -> scanAndAttack -> ...` forever, or until either phase's timeout/no-target/no-signal path calls `ctx.engine.Stop(...)`. `F6` force-stops and clears the overlay at any time.

**Shared-phase note (correcting `ARCHITECTURE.md`'s framing for a future agent)**: `ARCHITECTURE.md`'s "AutoFighter" section, written before `AutoFighterLoot` and `FruitStall` existed, says AutoFighter's two phases are "bot-specific" and not shared with anything. That is now **stale** — `ScanAndAttackPhase` and `WaitCombatPhase` were subsequently promoted into `Core/SharedPhases.ahk` and are now used by:
- **`Bots/AutoFighter/autofighter.ahk`** (this bot) — both phases, default next-phase-names (`"scanAndAttack"` for both).
- **`Bots/AutoFighterLoot/autofighter-loot.ahk`** — both phases, but passes `killNextPhaseName="lootPickup"` (adds a third phase, `LootPickupPhase`, that right-clicks a dropped item image and picks it up before returning to `scanAndAttack`).
- **`Bots/FruitStall/fruitstall.ahk`** — `WaitCombatPhase` only (not `ScanAndAttackPhase` — FruitStall's own `ThievingPhase` triggers combat by timing out on a loot-wait, not by scanning for a blob), with both `killNextPhaseName` and `retryNextPhaseName` explicitly passed as `"thieving"`.

**Any future change to `Core/SharedPhases.ahk` (especially `WaitCombatPhase` or `ScanAndAttackPhase`) must be re-verified against all three of these bots**, not just AutoFighter — load-check each one via `AutoHotkey64.exe /ErrorStdOut` (per `CURRENT_STATE.md`'s verification methodology) and, ideally, a live F5 check in-game, since a change that looks safe for AutoFighter's own defaults can silently break FruitStall's non-default `retryNextPhaseName` or AutoFighterLoot's non-default `killNextPhaseName` wiring.

## Config Reference
All keys are in `Config/auto-fighter-v2.ini`, sections `[Tunables]` and `[Settings]`.

| Section | Key | Meaning | Current value | If misconfigured |
|---|---|---|---|---|
| Tunables | `runnerTickMs` | Engine tick interval (ms). | `50` | Too high = laggy reaction to state changes; too low = wasted CPU on redundant ticks (busy-guarded, so not unsafe, just wasteful). |
| Tunables | `phaseTimeoutScan` | Engine-level hard timeout for `scanAndAttack` (ms) — independent of, and outside, `targetWaitTimeoutMs`. | `60000` | If lower than `targetWaitTimeoutMs`, the engine's generic timeout can fire (`Engine.Tick`'s `HasPhaseTimedOut` check) *before* the phase's own more specific "timed out waiting for a target" log/stop path runs, producing a less informative stop reason (`"Phase 'scanAndAttack' timed out"` instead of `"Timed out waiting for a target"`). Keep it comfortably above `targetWaitTimeoutMs`. |
| Tunables | `phaseTimeoutCombat` | Engine-level hard timeout for `waitCombat` (ms). | `60000` | Same risk as above, relative to `combatStartTimeoutMs` — must stay above it, and importantly must also stay above any realistic real fight duration, since `ResetPhaseTimer` is called every tick while `combatStartColor` is showing (see Known Risks: long-fight handling). |
| Tunables | `targetColor` | NPC overlay color to search for. | `0xFF00FF` (magenta) | Wrong color = `FindNearestBlobCenter` never finds anything → times out on every cycle, or (if it happens to match some other overlay/UI element) clicks the wrong thing. |
| Tunables | `targetColorTolerance` | Per-channel RGB tolerance for the blob color match. | `20` | Too tight = misses valid blob pixels under lighting/anti-aliasing variance, fragmenting one NPC into multiple false "blobs" or missing it outright. Too loose = risks matching a similarly-colored but unrelated screen element (see Known Risks: color-tolerance misclicks). |
| Tunables | `targetBlobRadius` | Half-size (px) of the box around the seed pixel used to compute the blob's centroid. | `48` | Too small = centroid biased toward whichever edge the seed pixel happened to land on (a real click precision problem, not just cosmetic). Too large = risks pulling in a *neighboring* NPC's pixels into the same centroid, aiming the click between two NPCs instead of on either one. |
| Tunables | `targetSampleRate` | Row stride for the centroid-computation scan. | `10` | Too high = coarser/less accurate centroid. Too low = more `PixelSearch`/`PixelGetColor`-equivalent calls, re-approaching the ~7ms/call performance cliff documented in `ARCHITECTURE.md`. |
| Tunables | `targetSeedRowStep` | Row stride for the initial nearest-blob seed search. | `10` | Same tradeoff as `targetSampleRate`, but for the seed step; too coarse risks skipping over a thin/small blob entirely between sampled rows. |
| Tunables | `refPointX` / `refPointY` | Fixed screen point representing "where the player is," used only to rank candidate blobs by distance. | `1249` / `702` | Wrong value doesn't break detection (the scan region is still centered here) but biases which NPC is treated as "nearest" when several are in range — could make the bot repeatedly pick a farther/wrong NPC over a closer one. |
| Tunables | `targetSearchRadiusX` / `targetSearchRadiusY` | Half-width/half-height (px) of the scan box around the ref point. | `400` / `400` | Too small = misses NPCs at the edge of the intended pen/area. Too large = re-approaches the whole-screen scan performance cliff (`ARCHITECTURE.md`: ~7ms/call `PixelSearch` overhead; a full 1440px-tall region took 2.5–30+s in the worst case observed). |
| Tunables | `scanPollMs` | Poll interval (ms) between scan attempts when nothing is found. | `100` | Too low = wastes CPU/PixelSearch calls retrying a scan that just failed. Too high = slower recovery after a miss. |
| Tunables | `targetWaitTimeoutMs` | Max time (ms) to wait for *any* target blob before `ScanAndAttackPhase` stops the engine. | `30000` | Too short = bot stops itself during a legitimate lull (e.g. all NPCs temporarily out of range/killed by someone else). Too long = a genuinely stuck bot (NPCs never spawn, wrong color configured) runs uselessly for a long time before stopping. |
| Tunables | `combatIndicatorX` / `combatIndicatorY` | Fixed screen pixel used as the combat-state indicator. | `2135` / `1265` | Wrong point = reads whatever color happens to be at that pixel (UI chrome, terrain, etc.) instead of the real HP/combat overlay — `WaitCombatPhase` would misbehave (see Known Risks). |
| Tunables | `combatIndicatorTolerance` | Per-channel RGB tolerance for matching `combatStartColor`/`combatKillColor`. | `20` | Too tight = misses the real color under minor rendering variance, causing spurious retries/timeouts. Too loose = risks the start/kill colors' tolerance windows overlapping each other or a third unrelated color, causing false state reads. |
| Tunables | `combatStartColor` | Indicator color while actively fighting. | `0x078A36` (green) | Wrong value = `WaitCombatPhase` never recognizes "fighting," so every real fight looks identical to "nothing happening yet," and the phase relies solely on the retry/timeout paths instead of tracking real combat. |
| Tunables | `combatKillColor` | Indicator color once a kill is confirmed. | `0x631413` (dark red) | Wrong value = kills are never detected as fresh; the bot would either loop forever in `waitCombat` until `combatStartTimeoutMs`, or (if it coincidentally matches something else) register false kills. |
| Tunables | `combatPollMs` | Poll interval (ms) while waiting on the indicator pixel. | `100` | Same responsiveness/CPU tradeoff as `scanPollMs`. |
| Tunables | `retryClickAfterMs` | If no indicator signal (start or kill) has appeared this long after the attack click, assume the click missed and retry scan+click. | `4000` | **Must stay comfortably above the measured ~3s kill-color linger** (death animation) — if lowered too close to or below that, a real fight-in-progress could still be showing stale kill-color residue past this deadline and get misread. See `combatStartTimeoutMs`'s comment in the `.ini` and the stale-kill-color guard section below. |
| Tunables | `combatStartTimeoutMs` | Outer ceiling (ms) for a combat signal to appear at all after the attack click, across all retries, before `WaitCombatPhase` stops the engine. | `10000` | Must be greater than `retryClickAfterMs` (the `.ini`'s own comment notes this — several retries are expected to happen before this ceiling trips). If set lower than or too close to `retryClickAfterMs`, few or zero retries get a chance to run before the hard stop. |
| Tunables | `postKillSettleDelayMs` | Delay (ms) after a confirmed kill before rescanning, to let the death animation/loot drop settle. | `100` | Too short = next scan may pick up residual death-animation pixels as a false blob, or click before the corpse/area visually clears. Too long = wasted idle time per kill, compounding over many cycles. |
| Tunables | `clickSettleMs` / `clickSettleJitterPercent` | Delay between mouse-move and click; jitter percent (currently inert, see Anti-Ban section). | `100` / `0` | Too short risks the client not registering hover before the click fires (a general framework-wide risk, not AutoFighter-specific). |
| Tunables | `ctrlHoldSettleMs` | Delay (ms) after pressing Ctrl (when `runMode=1`) before releasing it. | `100` | Too short risks the Ctrl-modifier not being registered by the client for the click. |
| Settings | `runMode` | `1` = hold Ctrl during every click (OSRS force-run/quick-action modifier); `0` = plain click. | `1` | Wrong setting could change which action a click performs in-game (e.g. force-attack vs. a context menu) depending on what's under the cursor — verify this matches the intended NPC-attack click behavior. |

## Known Risks & Edge Cases

- **Multiple NPCs in the search region** → **Current behavior**: `FindNearestBlobCenter` picks whichever blob's seed pixel is closest (by squared distance) to `(refPointX, refPointY)`, then centroids only around that one seed within `targetBlobRadius`. → **Risk/impact**: with several NPCs clustered within `targetBlobRadius` of each other, the centroid step (`FindCentroid`) can average in pixels belonging to a *different* NPC's overlay if their blobs overlap or sit closer together than `targetBlobRadius`, aiming the click at a point between two NPCs rather than on either one's centroid. There is no per-blob boundary detection — `FindCentroid`'s "nearest run per row" logic (`ColorSearch.ahk:283-307`) handles a single blob's own concave/notched shape, not disambiguating two separate nearby blobs.

- **Nearest blob isn't actually attackable** (a corpse mid-death-animation, a friendly/non-combat NPC sharing the same overlay color, another player) → **Current behavior**: `ScanAndAttackPhase` has no concept of NPC identity, aggro state, or attackability — it clicks purely on overlay color/position. → **Risk/impact**: if `targetColor` (`0xFF00FF`) is the game's generic NPC-highlight overlay rather than a hostility-specific color, the bot will click any matching overlay in range, including a dying NPC's lingering death-animation overlay (mitigated somewhat by `postKillSettleDelayMs`, but that's a fixed short delay, not a verified-cleared check) or a non-combat NPC if one happens to render the same overlay. A misclick here either does nothing useful (right-click menu on an unattackable target, or simply "walk here") or, worse, is silently swallowed since the bot has no result-verification step beyond the raw combat-indicator pixel — a click on the wrong thing just looks identical to "no combat signal yet" and falls into the retry path.

- **Color tolerance causing misclicks on similar-colored terrain/objects** → **Current behavior**: `targetColorTolerance=20` (per-channel RGB) is checked against the *entire* scan region, with no shape/size floor beyond `FindCentroid` needing at least one matching pixel in the `blobRadius` box. → **Risk/impact**: any terrain, ground clutter, or UI element that happens to fall within 20 per-channel units of `0xFF00FF` inside the scan box would be seeded and clicked exactly like a real NPC blob — magenta is a fairly unusual/saturated color for natural terrain, which limits (but does not eliminate) this risk in practice; it would need live verification if the fighting area's scenery is ever changed.

- **Attack click misses because the target moved** → **Current behavior**: this is exactly `retryClickAfterMs`'s job. If no `combatStartColor` or fresh `combatKillColor` appears within `retryClickAfterMs` (4000ms) of the click, `WaitCombatPhase` logs "No combat signal... retrying" and returns to `scanAndAttack` to re-scan and re-click, all while `combatStartTimeoutMs` (10000ms) keeps counting as an outer ceiling across all such retries. → **Risk/impact**: `retryClickAfterMs` vs `combatStartTimeoutMs` — the former guards "this *specific* click attempt seems to have missed, try again soon"; the latter guards "we've been retrying for too long overall with zero signal, something is more seriously wrong (stopping is safer than an infinite retry loop)." Getting `retryClickAfterMs` too low risks false retries during a real fight whose start-color hasn't rendered yet, or during the ~3s kill-color linger window (see stale-kill guard below) — though the stale-kill guard specifically prevents the *kill* half of that risk; the *start* half (real fight, slow-to-render start color) is only guarded by keeping `retryClickAfterMs` reasonably generous, not by any explicit code check.

- **Stale kill-color guard and instant kills** → **Current behavior** (`Core/SharedPhases.ahk:277-303`): on each entry to `waitCombat`, `entrySnapshotTaken`/`staleKillCleared` capture whether `combatKillColor` was *already* showing at that exact moment (leftover from the previous kill's ~3s death-animation linger). Only once the indicator is observed to leave that baseline (to background *or* to `combatStartColor` — not specifically "must see start color first") does a subsequent `combatKillColor` reading count as a genuinely fresh kill. This was fixed specifically to handle **instant kills** (an NPC weak enough to die before `combatStartColor` ever renders at all) — an earlier, incorrect fix required seeing `combatStartColor` first, which broke exactly this case by making instant kills wait out the full `retryClickAfterMs` for a start signal that would never come. → **Risk/impact for a future agent**: do not "simplify" this back to "wait for start color, then watch for kill color" — that regresses the instant-kill case. The current logic is deliberately "wait for the *previous* kill-color to clear, from whatever state, before trusting the *next* kill-color reading."

- **Window loses focus mid-fight** → **Current behavior**: both phases check `ctx.windowFocus.IsActive()` as their first line and return their own phase name (no-op tick) if focus is lost — no click, no state advance, no timer reset via `ResetPhaseTimer`. → **Risk/impact**: if focus is lost during a long real fight (`combatStartColor` showing), the phase timer is *not* being reset while unfocused (the reset only happens on the branch where `combatStartColor` actually matches, which requires reading the real pixel — but pixel reads still work even when the window isn't focused, since `PixelGetColor`/`PixelSearch` read screen contents regardless of focus). Re-read the code path carefully: the focus check is the *very first* line of `Run(ctx)` and returns immediately, before even checking the indicator color — so **the phase timer does NOT get reset while unfocused**, even if the fight is still visually ongoing underneath the unfocused window. If focus loss outlasts `phaseTimeoutCombat` (60000ms), the engine's own generic timeout (not `WaitCombatPhase`'s internal ones) will fire and stop the bot. This is arguably the correct conservative behavior (don't keep acting on a window that isn't focused) but means a long alt-tab during a fight can stop the bot even though the fight itself may have resolved fine.

- **No NPCs ever found (timeout path)** → **Current behavior**: `ScanAndAttackPhase` tracks `targetWaitStartedAt` (reset to 0 on every successful find) and calls `ctx.engine.Stop("Timed out waiting for a target")` once `targetWaitTimeoutMs` (30000ms) elapses with zero finds, then **returns `"scanAndAttack"` anyway** (moot, since `Engine.Stop` has already flipped `running` to false and cancelled the tick timer — see `Core/Engine.ahk:39-43`). → **Risk/impact**: none functionally (the engine is genuinely stopped, confirmed by reading `Engine.Stop`/`Tick`), but worth knowing for a future agent reading this phase in isolation: the return value after calling `Stop` is never actually consulted again, since `Tick()` won't run again once `this.running = false`.

- **Engine phase-timeout tripping during a long legitimate fight — recently fixed** → **Current behavior** (`Core/SharedPhases.ahk:315-320`): every tick that `combatStartColor` matches, `WaitCombatPhase` calls `ctx.failsafe.ResetPhaseTimer(ctx)` **unconditionally**, specifically commented as "not just the first [tick]... startColor still matching is proof this phase is making real progress (fighting), not stalled, so a long fight must not trip `phaseTimeoutCombat` just because it outlasts that budget." This is the fix referenced in the audit brief — before this fix, a real fight against a high-HP NPC that legitimately took longer than `phaseTimeoutCombat` (60000ms) to resolve would have been killed by the engine's own generic timeout, indistinguishable in the log from a genuinely stuck bot. → **Risk/impact now**: none, as long as `combatStartColor` keeps rendering/matching throughout the whole fight duration — if the indicator pixel itself is ever occluded (e.g. a UI overlay, chat box, or another window element covers `combatIndicatorX/Y` mid-fight) the reset stops firing and a long-but-legitimate fight could still trip the engine timeout in that specific scenario.

- **Two other logging/state fixes bundled into the same recent patch** (visible in the current code, worth a future agent knowing so they aren't "rediscovered" as new bugs): (1) a **missing "combat started" log** — `combatStartLogged` (`Core/SharedPhases.ahk:300,311-314`) is a one-shot latch so "Combat started. Waiting for kill." logs exactly once per fight, including the edge case where `combatStartColor` is already showing on the very first tick this phase runs (handled independently of `combatWaitStartedAt`, which would otherwise stay at its initial `0`/never-armed value and skip the log). (2) the **hardcoded next-phase-name** — `WaitCombatPhase`'s constructor now takes `killNextPhaseName` (default `"scanAndAttack"`) and `retryNextPhaseName` (defaults to `killNextPhaseName` if not passed) as real parameters instead of a hardcoded string, which is what makes `AutoFighterLoot`'s `"lootPickup"` hand-off and `FruitStall`'s `"thieving"` hand-off both possible from the same shared class.

- **Race between phase transitions and gate reads / scratch-state cleanup** → On checking `ScanAndAttackPhase.Run`'s exit path (`Core/SharedPhases.ahk:206-218`): every successful click resets `targetWaitStartedAt`, `entrySnapshotTaken`, and `combatWaitStartedAt` to fresh values before handing off to `waitCombat` — and `WaitCombatPhase` re-derives `staleKillCleared`/`combatStartLogged` itself on its next entry (`entrySnapshotTaken` gates this). No stale scratch state from a previous cycle was found carrying over incorrectly between `ctx.Get`/`ctx.Set` keys in this bot's two-phase loop — the reset points line up correctly for both the kill path and the retry path (both reset the same key set: `combatWaitStartedAt`, `entrySnapshotTaken`, `staleKillCleared`, `combatStartLogged`). This is a narrower, cleaner reset surface than the multi-phase bots (Motherlode etc.) specifically because AutoFighter only has two phases and no per-cycle "full loop" reset point to keep in sync.

## Anti-Ban / Human-Like Behavior Notes
- `Humanizer` is constructed as `Humanizer(false)` (`Bots/AutoFighter/autofighter.ahk:87`) — `enabled=false`. Per `ARCHITECTURE.md`, this is a **deliberate current-state choice for all bots in this framework**, not a bug specific to AutoFighter.
- With `enabled=false`: `Humanizer.Offset(...)` always returns `dx=0, dy=0` (no spatial click jitter), and `Humanizer.Jitter(baseMs, jitterPercent)` always returns `baseMs` unchanged (no temporal delay jitter) — see `Actions/Humanizer.ahk:18-39`.
- Concretely for this bot: every `ClickSettled` call (both phases exclusively use `ctx.clicker.ClickSettled(ctx, x, y, runMode)`) calls `MoveTo(x, y, 0, 0, ...)` with `width=0, height=0` — even if `Humanizer` were re-enabled, `Offset(0, 0, &dx, &dy)` would still return `dx=0, dy=0` (see `Humanizer.Offset`'s `maxX > 0`/`maxY > 0` guards), since neither phase ever passes a nonzero click-box width/height into `ClickSettled`. **So click-position jitter is currently a double no-op for this bot specifically**: disabled at the `Humanizer` level, and additionally never given a nonzero box to jitter within even if it were enabled.
- `clickSettleJitterPercent=0` in the `.ini` is consistent with (but not the sole cause of) jitter being inert — it would still be a no-op even at a nonzero value, since `Humanizer.enabled=false` short-circuits `Jitter()` before `jitterPercent` is ever used.
- Poll intervals (`scanPollMs`, `combatPollMs`) are fixed values from the `.ini`, not randomized — every poll waits exactly the configured `baseMs` via `Waiter.After`, since the jitter function it's given (`Humanizer.Jitter`) is currently a pass-through.
- Per `ARCHITECTURE.md`'s Config section: "don't add *new* jitter-related keys to future bots, but don't strip the existing ones either without being asked" — this applies here too; the inert `clickSettleJitterPercent` key should be left in place.

## Bugs Found This Audit
No new correctness bugs were found in `Bots/AutoFighter/autofighter.ahk`, `Config/auto-fighter-v2.ini`, or the parts of `Core/SharedPhases.ahk` this bot exercises, beyond what CURRENT_STATE.md/ARCHITECTURE.md already document as fixed (the stale-kill-color guard, the missing combat-started log, the hardcoded next-phase-name, and the long-fight phase-timeout reset). One **documentation-accuracy issue** was found and is called out above rather than filed as a code bug: `ARCHITECTURE.md`'s AutoFighter section still describes `ScanAndAttackPhase`/`WaitCombatPhase` as bot-specific/unshared, which is stale now that both `AutoFighterLoot` and `FruitStall` construct `WaitCombatPhase` (and `AutoFighterLoot` also constructs `ScanAndAttackPhase`) from `Core/SharedPhases.ahk`. This doesn't affect AutoFighter's own runtime behavior, but a future agent editing `ARCHITECTURE.md` itself, or reasoning about "is this phase safe to change," should know the shared-usage list above is broader than that document currently states.

## Future Agent Development Roadmap
- **Verify any `Core/SharedPhases.ahk` change against all three consumers before considering it done**: AutoFighter (`scanAndAttack`/`waitCombat` defaults), AutoFighterLoot (`killNextPhaseName="lootPickup"`), FruitStall (`killNextPhaseName`/`retryNextPhaseName` both `"thieving"`, `WaitCombatPhase` only). Load-check each with `AutoHotkey64.exe /ErrorStdOut` per `CURRENT_STATE.md`'s stated verification methodology, then a live F5 check if the change touches logic (not just comments).
- **Consider a per-blob exclusion/second-nearest fallback** for the "multiple NPCs in the search region, centroid pulls toward a neighbor" risk above — e.g. after computing a centroid, verify a minimum run-length/pixel-count within `targetBlobRadius` actually belongs to one contiguous blob before clicking, or re-run the seed search from the *previous* target's last known position to avoid re-picking the same NPC's corpse.
- **If future NPCs share `targetColor` with non-attackable entities** (other players, friendly NPCs, corpses mid-animation), the cleanest fix given this framework's existing primitives is likely a distinct overlay color check rather than new detection code — confirm with live observation whether OSRS renders a different overlay color/hue for non-hostile vs. hostile targets before adding logic to distinguish them.
- **`retryClickAfterMs`'s "real fight, slow-to-render start color" gap is currently unguarded** (unlike the symmetric stale-kill-color case, which has an explicit baseline guard) — if slow start-color rendering turns out to cause false retries live, the fix pattern would mirror the existing stale-kill guard: snapshot whether the *fight itself* might already be in progress by some other signal before trusting a "no signal yet" retry.
- **The window-focus-loss-during-a-real-fight interaction** documented in Known Risks (phase timer doesn't reset while unfocused, even though pixel reads still succeed) is a candidate for a future explicit design decision: either accept it as correctly conservative, or special-case "focus lost but combat pixel still shows fighting" to keep resetting the timer purely from the pixel read regardless of focus state.
- **No result-verification beyond the raw combat-indicator pixel** — a misclick on an unattackable entity is currently indistinguishable from "click landed, fight hasn't started yet" until `retryClickAfterMs` elapses. A future hardening pass could add a secondary confirmation signal (e.g. a chat-box combat message anchor, if one exists) to shorten the effective misclick-recovery latency below the current 4000ms.
- **This bot has no loot/food/prayer step by design** — if it's ever extended to need one, follow `AutoFighterLoot`'s existing pattern (a third phase constructed with a non-default `killNextPhaseName`) rather than modifying `WaitCombatPhase`'s defaults, to avoid touching the shared class's behavior for the other two consumers.
