# MotherlodeFixed

## Overview

Mines pay-dirt at the Motherlode Mine, but for a **stand-still setup**: the character stays on one tile for the entire mining loop, with exactly two pay-dirt veins in fixed, calibrated screen positions reachable from that tile. There is no hopper — mined pay-dirt goes straight into a bank-style deposit box (a "sack"-free workflow), so once the inventory's indicator slot fills, the bot walks off the tile only once (a single click) to reach the deposit box, deposits, then clicks a single point to walk back and resume.

- **Relationship to `Bots/Motherlode`**: this **specializes**, not supersedes, plain `Motherlode`. It is a **structural rewrite for a different physical setup**, not a bugfix of the same setup. Plain `Motherlode` models a mining spot with **two veins the character must walk between**, rockfalls that block a walkway, a **hopper** to deposit ore into, and a **separate ore sack** to withdraw from before banking — a multi-tile, multi-waypoint course requiring `TargetLock`-based moving-target tracking (`ColorSearch.FindFilledBlock` over a wide region + acquire/track state). `MotherlodeFixed` models a setup where **both veins are visible and clickable without moving** and pay-dirt deposits directly into a bank-style container (no hopper, no sack, no rockfalls) — so its detection collapses to two fixed-point color checks (`VeinChecker`) instead of a region search, and its state machine collapses from 7 phases to 3. The two bots are **meant to coexist**: they target different vein layouts/rooms in the Motherlode Mine, each with its own `.ini`, log file, and Phase classes. Neither file includes or references the other's config or code. Do not delete/deprecate `Bots/Motherlode` on the assumption this replaces it — it doesn't, unless the operator has confirmed they only ever mine from the stand-still spot.
- **Start location / setup assumptions**: character standing on the single calibrated mining tile, with both `veinA` and `veinB` (pay-dirt overlay colors) visible on screen without any camera movement, and the deposit box marker (`depositMarkerX/Y`, a magenta `0xFF00FF` UI marker) and the "Deposit All" button both reachable from that same tile without extra walking beyond the two configured clicks. RuneLite client window in the same position/size used during calibration (the hardcoded inventory grid and every fixed screen coordinate assume this).
- **Required calibration**: `veinAX/Y` + `veinAColor`, `veinBX/Y` + `veinBColor`, `veinBlockW/H`, `depositMarkerX/Y`, `depositImageAnchorX/Y`, `returnClickX/Y` — all screen-position-dependent and must be recalibrated if the client window moves/resizes or a different stand-still spot/vein pair is used.

## State Machine

Three phases, `mine -> depositBank -> returnToMine -> mine`. Started on `F5` (`botEngine.Start("mine")`), stopped on `F6` (`botEngine.Stop("Stopped (F6)")` + `botOverlay.Clear()`).

### `mine` (`MinePhase`, timeout `phaseTimeoutMine` = 180000ms)

- Window-focus guard first (`ctx.windowFocus.IsActive()`), as in every phase of both bots.
- **If inventory full** (`ctx.inventory.IsFull()`, gated on `indicatorSlot` = slot 28 alone — see Config Reference): logs, clears `activeVein` + resets its own `MissDebounce`/`_wasMissing`, resets `depositPreDelayApplied`/`returnClicked`/`returnWaitStartedAt` scratch keys used by the two downstream phases, transitions to `depositBank`.
- **Else, if a vein is already locked in** (`ctx.Get("activeVein")` is `"A"` or `"B"`): checks **only that vein's** fixed point via its `VeinChecker.IsActive(...)` (a padded `ColorSearch.FindFilledBlock` at a known point — no click, no search elsewhere). Feeds the result into a `MissDebounce` (see below). While not yet "lost" (fewer than `veinMissingTicksToUnlock`=3 consecutive misses), stays in `mine` with no action — mining is presumed still in progress. On a genuine recovery (found again after having been missing at all), calls `ctx.failsafe.ResetPhaseTimer(ctx)` — real progress, extends the 180s ceiling. Once truly lost (3 consecutive misses), clears `activeVein` and falls through to re-acquire in the same tick.
- **Else (no vein locked)**: checks vein A first, then vein B (A preferred if both are simultaneously active — same tie-break bias as plain Motherlode's reference-point-distance tie-break, just simpler since there are only two fixed candidates instead of an open search). On finding either, clicks it (`ctx.clicker.ClickSettled`, honoring `runMode`), sets `activeVein` to `"A"`/`"B"`, resets the debounce, resets the failsafe timer, stays in `mine`.
- **Else (neither vein active)**: throttles via `ctx.waiter.After(ctx.timing, "minePoll")` (100ms base) rather than polling at the raw 50ms engine tick rate, stays in `mine`.
- `ResetForNewCycle()`: resets the `MissDebounce` and `_wasMissing`. Called by `ReturnToMinePhase` on arrival, alongside every other phase's per-cycle reset.

### `depositBank` (`DepositBankPhase`, timeout `phaseTimeoutBank` = 30000ms)

- Window-focus guard.
- One-time settle delay (`depositPreClickDelay`, 100ms base) applied via a `depositPreDelayApplied` scratch flag **before** searching — matches plain Motherlode's "delay before search, not after" rule (ARCHITECTURE.md pattern #4).
- Searches a small **padded region around a fixed point** (`depositMarkerX/Y` ± `depositSearchPaddingPx`=20) for the magenta deposit-container marker (`depositColor`=`0xFF00FF`, `depositTolerance`=0, `depositBlockW/H`=27x27) — **not** a full-screen search like plain Motherlode's `DepositBankPhase` (`ColorSearch.FindFilledBlock(0, 0, A_ScreenWidth, A_ScreenHeight, ...)`), because the character never moves, so the marker is always at (approximately) the same point.
- If not found: logs "Cannot see deposit container!", waits `depositMarkerPoll` (100ms), stays in `depositBank` (no timeout-driven `engine.Stop` on this specific branch — only the outer `phaseTimeoutBank`/image-wait timeout below can end the phase).
- If found: clicks it, resets the failsafe timer, then calls `depositAnchor.WaitFor(...)` (an `ImageAnchor` on `Images/deposit-motherlode.png`, region = `depositImageAnchorX/Y` ± `depositImageSearchPaddingPx`=20, bounded by `depositImageWaitTimeoutMs`=15000ms, polling every `depositImagePoll`=100ms). On timeout, logs and calls `ctx.engine.Stop(...)` (clean stop, not a throw) and returns `depositBank` (engine is already stopped by then, so this return value is moot).
- On success: clicks the found "Deposit All" button center, logs, transitions to `returnToMine`.

### `returnToMine` (`ReturnToMinePhase`, timeout `phaseTimeoutReturn` = 30000ms)

- Window-focus guard.
- One-shot click gated by `returnClicked` scratch flag: clicks the single fixed `returnClickX/Y` point once, sets `returnClicked=true`, resets the failsafe timer, stays in `returnToMine`.
- Every subsequent tick: checks **either** vein's fixed point via the same `VeinChecker`s used by `MinePhase` (`veinCheckerA.IsActive(veinA) || veinCheckerB.IsActive(veinB)`) — this is the arrival confirmation, since seeing a vein active again means the character is back on the mining tile with line of sight to at least one vein.
  - If either is visible: logs arrival, does the **full per-cycle reset** (`activeVein`, `depositPreDelayApplied`, `returnClicked`, `returnWaitStartedAt`, plus calling `ResetForNewCycle()` on every phase in `nextCyclePhases` = `[botDepositBankPhase, botReturnToMinePhase]`), transitions back to `mine`.
  - Else: tracks `returnWaitStartedAt` (set on first miss), and if `(A_TickCount - waitStartedAt) > returnWaitTimeoutMs` (30000ms), logs a timeout message and calls `ctx.engine.Stop(...)` cleanly. Otherwise waits `returnVeinPoll` (100ms) and stays in `returnToMine`.

## Diff vs. `Bots/Motherlode`

This is a **rewrite for a different physical mining setup**, not a patch to the same one. Concrete differences:

1. **Phase count/shape: 7 phases collapse to 3.** Plain Motherlode: `mine -> clearRed -> clearYellow -> withdrawSack -> depositBank -> returnMine1 -> returnMine2 -> mine` (`Bots/Motherlode/motherlode.ahk:914`, engine wiring). MotherlodeFixed: `mine -> depositBank -> returnToMine -> mine` (`Bots/MotherlodeFixed/motherlode-fixed.ahk:494-501`). `clearRed` (rockfall clearing), `clearYellow` (hopper deposit), and `withdrawSack` (ore-sack withdrawal) have **no equivalent at all** — this setup has no hopper, no ore sack, and (implicitly) no rockfall obstruction to clear, or it's simply not modeled/handled. `returnMine1`/`returnMine2`'s 2-stage, 2-waypoint-marker walk-back (`Bots/Motherlode/motherlode.ahk:542-738`) collapses into `ReturnToMinePhase`'s single click + single vein-visibility check (`Bots/MotherlodeFixed/motherlode-fixed.ahk:321-379`), since only one click is needed to get back onto the one tile.

2. **Vein detection: region search + `TargetLock` replaced by two fixed-point checks + `MissDebounce`.** Plain Motherlode's `MinePhase._Acquire`/`_Track` (`Bots/Motherlode/motherlode.ahk:121-216`) searches a wide region (`mineRegionX1/Y1/X2/Y2` = a ~370x170px box) for either of two vein *colors* (light/dark variants of the same vein, `veinColorLight`/`veinColorDark`), picks whichever is closer to a reference point when both are visible, then tracks the found vein's *position* with a `TargetLock` (`stableTicksRequired`, `moveTolerancePx`) since the vein's on-screen position can drift as the character walks/camera moves. MotherlodeFixed's `VeinChecker.IsActive()` (`Bots/MotherlodeFixed/motherlode-fixed.ahk:56-88`) checks two **separate, always-stationary** veins (`veinA`/`veinB`, each its own fixed color) at their own **fixed points** — no position tracking needed since the character never moves the camera far enough to shift a vein's screen position. `TargetLock` is entirely unused by this bot (not even `#Include`d — confirm via the include list at `motherlode-fixed.ahk:21-35`, which omits `Detection/TargetLock.ahk` that plain Motherlode includes at `motherlode.ahk:27`).

3. **`MissDebounce` is a new, purpose-built class replacing an implicit reliance on `TargetLock`.** The comment block at `motherlode-fixed.ahk:90-99` explicitly documents this: an earlier version of this bot (or a design considered and rejected) borrowed `TargetLock` for "has this fixed point been missing N ticks," but that required disabling most of what `TargetLock` does (`stableTicksRequired=0`, `moveTolerancePx=0`, dummy coordinates) — "a fragile implicit dependency on `TargetLock`'s internals never changing to consult those now-inert fields." `MissDebounce` (`motherlode-fixed.ahk:100-117`) is a ~15-line class that does exactly one thing: count consecutive `Observe(found)` misses and expose `IsLost()`. This is the single clearest "fix" in this bot — not a bug fix in the traditional sense, but a **correctness/maintainability fix for a code smell**: using a class via disabling most of its behavior is fragile against future changes to that class.

4. **Overlapping padded search boxes are fixed by construction, not by relying on color-tolerance separation.** `VeinChecker.IsActive` (`motherlode-fixed.ahk:66-87`) clamps each vein's padded search box at the midpoint between the two veins whenever `otherVeinX/Y` is supplied — and the wiring at `motherlode-fixed.ahk:470-471` always supplies it (`botVeinCheckerA` is built with veinB's position, `botVeinCheckerB` with veinA's). This is confirmed *necessary*, not defensive-only: with the current `.ini` values (`veinAX/Y`=1198,697; `veinBX/Y`=1240,740; `veinBlockW/H`=23; `veinSearchPaddingPx`=15), each vein's *unclamped* padded box is `26px` half-width/height, giving vein A the box `x:[1172,1224] y:[671,723]` and vein B the box `x:[1214,1266] y:[714,766]` — these overlap in `x:[1214,1224] y:[714,723]`. Without the midpoint clamp, a color match for vein B could be found while scanning inside vein A's nominal search box (or vice versa) if the two vein colors (`0x00FF00` vs `0x009B00`) ever fell within `veinTolerance`=20 of each other in that overlap region. Plain Motherlode has no equivalent concept (its single mine region is one box, not two independently-padded ones), so this is a genuinely new problem this design introduces, and a genuine fix for it — the code comment at `motherlode-fixed.ahk:49-54` states this makes the padding "safe by construction instead of relying on the two vein colors happening to differ by more than the color tolerance," implying the older/unclamped version *was* relying on exactly that fragile assumption.

5. **No hopper/sack -> single indicator slot suffices for "full."** Plain Motherlode requires **both** slot 28 AND slot 27 occupied to count as full (`AndGate`, `motherlode.ahk:857-863`), because a lone gem can land in slot 28 without the hopper actually having collected pay-dirt into the rest of the inventory — the hopper is a separate, fallible, multi-click step that could leave the inventory in an ambiguous state. MotherlodeFixed uses **only** `indicatorSlot`=28 via a plain `SlotGate` (`motherlode-fixed.ahk:459-461`), because it deposits directly into a bank-style deposit box that accepts any item — there's no failed-hopper-collection case to guard against. This is a **legitimate simplification for the new setup**, not a regression: the two-slot AND-gate exists specifically to compensate for the hopper's failure mode, which doesn't exist here.

6. **`DepositBankPhase`'s marker search is a small padded region, not a full-screen scan.** Compare `motherlode-fixed.ahk:279-286` (`FindFilledBlock` over `markerX/Y ± searchPaddingPx`) to `motherlode.ahk:509-510` (`FindFilledBlock(0, 0, A_ScreenWidth, A_ScreenHeight, ...)`). Consistent with the "character never moves" premise — the deposit marker is always near the same point, so a full-screen scan would be pure wasted `PixelSearch` cost (recall ARCHITECTURE.md's ~7ms/call cost figure) for no added correctness.

7. **Config keys renamed and restructured, not shared.** `auto-motherlode-fixed.ini` (`Config/auto-motherlode-fixed.ini`) has its own key names (`veinAX/Y/Color`, `veinBX/Y/Color`, `depositMarkerX/Y`, `returnClickX/Y`, etc.) distinct from `auto-motherlode-v2.ini`'s (`mineRegionX1/Y1/X2/Y2`, `return1ClickX/Y`, `return2ClickX/Y`, `sackRunX/Y`, `bankColor`, etc.) — the two `.ini`s share no keys and are loaded by entirely separate `Config` instances (`iniPath` values differ: `motherlode-fixed.ahk:436` vs `motherlode.ahk:838`). Confirms these are independently-tunable bots, not one bot with a config variant (unlike Smelter's `smelter-gold.ini`/`smelter-mithril.ini`, which share one code file and one schema).

8. **`runMode=1` in both `.ini`s** (force-run/Ctrl-click held during every click) — unchanged between the two bots.

**Not changed / directly reused**: `ClickSettled`'s settle-delay-before-click pattern, the "delay before search, not after" rule for the deposit pre-click delay, the bounded-wait-then-clean-stop failsafe pattern (`engine.Stop(...)`, never throw), the window-focus guard as the first line of every phase, the `nextCyclePhases` reset-on-arrival pattern, and the inventory grid layout constants (`firstX=2099, firstY=801, cols=4, rows=7, slotW=72, slotH=64, gapX=12, gapY=8` — identical in both files, `motherlode-fixed.ahk:453` vs `motherlode.ahk:855` — same client window).

## Config Reference

All keys in `Config/auto-motherlode-fixed.ini`, `[Tunables]` unless noted.

|---|---|---|---|
| `runnerTickMs` | Engine tick interval | 50 | Too low = wasted CPU on idle ticks; too high = sluggish phase transitions and click cadence |
| `phaseTimeoutMine` | Force-stop if `mine` makes no progress this long | 180000 | Too low: a long, genuinely uninterrupted mining stretch (both veins non-active but taking forever) is never expected to sit here without progress being recorded — a false stop is more likely from a stuck/miscalibrated vein check; too high: a truly stuck bot (e.g. permanently-active stray pixel, see Known Risks) runs unattended far longer before stopping |

## Known Risks & Edge Cases

- **Scenario**: A stray rockfall, NPC, or graphical effect happens to render at or near `depositMarkerX/Y` or either vein's fixed point, matching the configured color within tolerance. → **Current behavior**: `VeinChecker.IsActive`/`DepositBankPhase`'s search would report a false positive — there's no secondary confirmation (e.g. a second sample point elsewhere) beyond `VerifyBlock`'s 5-point cross-check within the same detected blob. → **Risk/impact**: a false-positive vein could be "clicked" (i.e. `MinePhase` fires a click at a coordinate that isn't actually an active vein), wasting a click cycle; more seriously, a persistent false-positive at a vein's fixed point (e.g. a UI element that never goes away) would make `MissDebounce.IsLost()` never fire, permanently locking `activeVein` and starving the "check for full inventory" logic of any actual mining progress — though `IsFull()` is checked unconditionally every tick regardless of `activeVein` state, so the bot would still eventually transition to banking once genuinely full, just without ever having mined further ore in the interim.
- **Scenario**: Both veins are simultaneously active. → **Current behavior**: `MinePhase`'s no-target branch always checks vein A first, silently preferring it every time this happens (`motherlode-fixed.ahk:207-216`). → **Risk/impact**: not a bug per se (documented and intentional, matching plain Motherlode's closer-vein tie-break spirit), but means vein B could be left un-mined indefinitely if vein A is reliably reactivated before B is ever chosen — a minor efficiency loss, not a correctness bug.
- **Scenario**: The client window moves or is resized after calibration. → **Current behavior**: every fixed coordinate (`veinAX/Y`, `veinBX/Y`, `depositMarkerX/Y`, `depositImageAnchorX/Y`, `returnClickX/Y`, plus the hardcoded inventory grid) silently searches/clicks the wrong screen location. → **Risk/impact**: total failure — likely manifests as repeated "Cannot see deposit container!" log lines or veins never detected, eventually timing out. No runtime check verifies the window is still where it was calibrated.
- **Scenario**: `veinSearchPaddingPx` is increased significantly in a future `.ini` edit without re-verifying vein spacing. → **Current behavior**: the midpoint-clamp logic in `VeinChecker.IsActive` (`motherlode-fixed.ahk:74-81`) keeps the two padded search boxes from ever crossing the midpoint between the veins, regardless of how large the padding gets — so this specific overlap failure mode is now structurally prevented. → **Risk/impact**: low, this is the one edge case the code was explicitly hardened against. However, if padding is increased so much that a vein's *clamped* box no longer contains that vein's own fixed point with any slack (i.e. padding grows well past half the inter-vein distance), `VerifyBlock`'s 75%-of-block-size check could still fail to find the vein at all — a different failure mode (missed detection, not cross-vein false match) that isn't specifically guarded against.
- **Scenario**: Neither vein is active on entering `mine` fresh at the very start of a run (`F5` pressed while pay-dirt happens to be between spawns/depleted with no animation showing). → **Current behavior**: falls straight to the `minePoll` throttled wait branch, polling both fixed points at 100ms intervals indefinitely — no `phaseTimeoutMine`-independent inner timeout on "waiting for first vein," only the outer 180s phase timeout. → **Risk/impact**: acceptable — this is expected steady-state behavior (waiting for a vein to spawn/respawn), not an error condition; the 180s ceiling is the real backstop, but note it only trips if there's truly zero progress (no click, no recovery-from-miss) for a full 180s.
- **Scenario**: `DepositBankPhase` finds the deposit marker but the "Deposit All" image never appears (e.g. deposit box UI changed, image stale, click missed the actual marker target due to a UI overlay). → **Current behavior**: waits up to `depositImageWaitTimeoutMs` (15s), then logs and calls `ctx.engine.Stop(...)` — a clean, attended-friendly stop, not an infinite loop. → **Risk/impact**: correct failure mode; operator needs to notice the bot stopped and re-verify calibration.
- **Scenario**: `ReturnToMinePhase` never sees either vein reappear (return click missed, walked to the wrong spot, or the mining tile's veins are both genuinely and permanently depleted with no respawn in sight). → **Current behavior**: waits `returnWaitTimeoutMs` (30s) then calls `ctx.engine.Stop(...)`. → **Risk/impact**: correct failure mode, same as above.
- **Scratch-state reset completeness**: `MinePhase`'s inventory-full branch resets `activeVein`, its own debounce, `depositPreDelayApplied`, `returnClicked`, `returnWaitStartedAt` — this matches exactly the scratch keys `DepositBankPhase` and `ReturnToMinePhase` read (`depositPreDelayApplied` in the former; `returnClicked`/`returnWaitStartedAt` in the latter). `ReturnToMinePhase`'s own arrival branch repeats the same reset plus calls `ResetForNewCycle()` on `nextCyclePhases` (itself and `DepositBankPhase`, both of which are documented as no-ops since they hold no phase-local state needing a cycle reset). Cross-checked against every `ctx.Set`/`ctx.Get` call in the file — no orphaned scratch key was found that's written but never reset between cycles.

## Anti-Ban / Human-Like Behavior Notes

- **`Humanizer(false)`** — constructed with `enabled=false` at `motherlode-fixed.ahk:441`, identical to every other bot in the framework (per ARCHITECTURE.md, a deliberate, framework-wide choice, not an oversight specific to this bot). This means:
  - `Clicker.MoveTo`'s spatial jitter (`Humanizer.Offset`) is a no-op — every click lands exactly on the computed center point (vein center, deposit marker center, deposit-button image center, or the fixed return-click point), with zero pixel-level randomization.
  - `Waiter`'s injected jitter function (`(baseMs, jitterPercent) => botHumanizer.Jitter(baseMs, jitterPercent)`, wired at `motherlode-fixed.ahk:444`) always returns `baseMs` unchanged — every configured delay (`clickSettleMs`, `depositPreClickDelayMs`, `minePollMs`, etc.) fires at exactly its configured value, tick after tick, cycle after cycle. `clickSettleJitterPercent=10` in the `.ini` is present but currently inert.
- **Poll intervals are fixed, not randomized**: `minePollMs`=100, `depositMarkerPollMs`=100, `depositImagePollMs`=100, `returnVeinPollMs`=100 — all identical round values, and all effectively unjittered per the above. A pattern-detection system watching click/poll timing would see perfectly uniform intervals.
- **Click cadence**: no per-click randomized cooldown range — `veinMissingTicksToUnlock`/poll-driven timing is deterministic given fixed inputs.
- **`runMode=1`**: every click is wrapped in a held Ctrl (force-run modifier), consistent across all three phases.
- **Net assessment**: this bot has strictly less inherent detection-surface variability than a human player, by design choice inherited from the framework (not a regression introduced by this bot specifically) — anti-ban posture is currently "the mechanism exists and is wired in, but switched off," same as documented in ARCHITECTURE.md for the other bots.

## Bugs Found This Audit

No functional bugs were found in `motherlode-fixed.ahk` itself during this audit — the file is small, internally consistent, and its own comments already document the specific design problems it solves (the `TargetLock`-abuse smell, the overlapping-search-box hazard). Two minor observations, not correctness bugs:

- **`Bots/MotherlodeFixed/motherlode-fixed.ahk:288-292`**: on failing to find the deposit marker, `DepositBankPhase` logs and waits, but does not track a "how long have we failed to see the marker" inner timestamp the way `ReturnToMinePhase` does for its vein-reappearance wait — it relies entirely on the outer `phaseTimeoutBank` (30s) via `FailSafe`'s "no `ResetPhaseTimer` call" mechanism. This works correctly (the failsafe does fire), but means the log has no equivalent "Timed out waiting for..." message specific to the marker-not-visible case — when this phase stops via the generic Engine-level `"Phase 'depositBank' timed out"` message (from `Engine.Tick()`, not from the phase's own code), a future agent reading the log won't immediately see the phase's own diagnosis of *why* — only plain Motherlode's `WithdrawSackPhase`/`ReturnMine1/2Phase` pattern of self-tracked wait-timeouts with a phase-specific log message before `engine.Stop(...)` gives that detail. This is a minor logging/diagnosability gap, not a functional defect.
- **Indicator slot documentation duplication**: the comment at `motherlode-fixed.ahk:455-458` and the `.ini` comment at `Config/auto-motherlode-fixed.ini:106-110` both explain the same "no hopper, so single slot suffices" reasoning almost verbatim — harmless, but a future edit to one explanation risks drifting from the other.

## Future Agent Development Roadmap

- **Do not deprecate `Bots/Motherlode`.** The two bots address genuinely different physical mining setups (multi-tile course with hopper/sack/rockfalls vs. stand-still two-vein spot with direct bank deposit) — confirmed by the total absence of shared config keys, the absence of `TargetLock`/rockfall/hopper/sack code in `MotherlodeFixed`, and the explicit file-header comment stating the two never touch each other's code/config. Only reconsider this if the operator confirms the multi-tile course is no longer used at all.
- **If a third stand-still variant is ever needed** (a different vein pair/room), follow the Smelter `.ini`-variant pattern noted in ARCHITECTURE.md: same `motherlode-fixed.ahk` code, a new `Config/auto-motherlode-fixed-<variant>.ini`, repoint `iniPath` (or duplicate the bot folder) — do not fork the phase classes unless the new spot needs a structurally different check (e.g. three veins instead of two, which `VeinChecker`/`MinePhase` don't currently generalize to).
- **Consider adding a phase-local timeout diagnostic to `DepositBankPhase`'s marker-not-found branch**, mirroring `ReturnToMinePhase`'s `returnWaitStartedAt` pattern, so a log reader sees a specific "Timed out waiting for deposit marker" message before the generic Engine-level phase-timeout message — purely a diagnosability improvement, not required for correctness (see Bugs Found This Audit).
- **If this bot is ever extended to more than two veins**, `MinePhase`/`VeinChecker`'s current design (hardcoded veinA/veinB parameters, pairwise midpoint clamp) does not generalize past two — would need an array of veins and an N-way clamp (e.g. Voronoi-style nearest-neighbor midpoint per pair, or just non-overlapping regions verified at calibration time) rather than a straightforward parameter extension.
- **Humanizer/jitter remains intentionally inert**, per the framework-wide convention documented in ARCHITECTURE.md — don't enable it or add new jitter keys to this bot without being asked; don't strip the existing (currently-inert) `clickSettleJitterPercent` key either.
- **Before touching calibration values**, re-verify the padded-box overlap arithmetic in the Diff section above (vein spacing vs. `veinSearchPaddingPx`) still holds if `veinAX/Y`/`veinBX/Y` are ever recalibrated — the midpoint clamp handles overlap safely regardless, but a large enough padding change could shrink a vein's *effective* (clamped) search box below what `VerifyBlock` needs, causing missed detections rather than false cross-vein matches.
