# Firemaking

## Overview
Burns logs from inventory at a single fixed ground spot, then banks to restock, on a repeating loop. Every cycle: walk to (click) a fixed firemaking marker, confirm the burn dialog, press `space` and wait for the inventory to empty (the game auto-burns logs one by one; the bot does not click each individual log), walk to (click) a fixed bank marker, wait for the bank interface, withdraw logs from one bank slot, then loop back to the fire spot.

This is one of the simplest bots in the framework — it wires together **only** the two shared generic phases from `Core/SharedPhases.ahk` (`PressAndWaitEmptyPhase` for burning, `GoToBankPhase` for banking) plus two small bot-specific phases (`GoToFirePhase`, `WithdrawLogsPhase`) that are themselves thin variations on the same "verify marker → click → wait for anchor" and "withdraw-plan loop" shapes documented in `ARCHITECTURE.md`. See `ARCHITECTURE.md` for the shared-phase contracts, gate/anchor primitives, and general framework rules (config-driven, `Waiter`-only sleeps, etc.) — this document only covers what's specific to Firemaking.

- **Start location / setup assumption**: player standing near a calibrated firemaking spot with a full inventory of logs already in hand, OR out of logs and ready to bank first (the state machine always starts at `goToFire`, so if logs are already gone the fire-marker click sequence will simply time out per `fireMarkerWaitTimeoutMs`/`craftMarkerWaitTimeoutMs` unless a human manually starts the bot from a banked state — there's no "detect empty inventory at boot and skip to bank" logic).
- **Required calibration** (all screen-position/color/image values, all `.ini`-backed):
  - `fireMarkerX/Y` + `fireMarkerColor` (green, `0x00FF00`) — a fixed ground-tile overlay marker for where to click to start burning.
  - `craftMarkerAnchorX/Y` + `Images/craft-marker-1.png` — the "burn logs" dialog confirmation image.
  - `bankMarkerX/Y` + `bankMarkerColor` (blue, `0x0000FF`) — the bank booth/chest marker.
  - `bankOpenAnchorX/Y` + `Images/deposit-default.png` — used purely as a "bank interface is open" signal (never clicked as deposit-all by this bot).
  - `bankSlotFirstX/Y` + `bankSlotPitchX/W/H` — bank slot coordinate math for withdrawing.
  - Inventory pixel grid (`firstX=2099, firstY=801, cols=4, rows=7, slotW=72, slotH=64, gapX=12, gapY=8`) — hardcoded in `firemaking.ahk` (not `.ini`), shared verbatim with Motherlode/other bots on this same client window.

## State Machine

`goToFire -> burnLogs -> goToBank -> withdrawLogs -> goToFire`

| Phase | Shared or bot-specific | Construction / behavior |
|---|---|---|
| `goToFire` (`GoToFirePhase`, `firemaking.ahk:48-120`) | **Bot-specific** (not in `SharedPhases.ahk` — structurally identical to `GoToBankPhase` but not unified per `ARCHITECTURE.md`'s "Not (yet) unified" note) | Searches for the green fire marker via `ColorSearch.FindFilledBlock` in a region padded `fireMarkerSearchPaddingPx` (30px) around `(fireMarkerX, fireMarkerY) = (1532, 537)`. If not found, re-clicks the fixed point `(fireMarkerX, fireMarkerY)` every `fireMarkerReclickCooldownMs` (6000ms) until found or `fireMarkerWaitTimeoutMs` (30000ms) elapses (then `ctx.engine.Stop(...)`). Once found, clicks the marker's *detected* center once (latched via `fireMarkerClicked` scratch flag), then calls `craftAnchor.WaitFor(...)` polling for `Images/craft-marker-1.png` every `craftMarkerPollMs` (100ms) up to `craftMarkerWaitTimeoutMs` (15000ms). Transitions to `burnLogs` once the dialog image appears. |
| `burnLogs` (shared `PressAndWaitEmptyPhase`) | **Shared** | Constructed at `firemaking.ahk:326`: `PressAndWaitEmptyPhase("burnLogs", botKeyAction, "space", "spacePressSettle", "goToBank")`. Key pressed is the **space key** (`KeyAction.Press("space")` → `Send("{space}")`) — this is a dialog confirmation keypress, **not a numbered inventory-slot key**, and **no log is ever clicked directly**; the actual burning is done entirely by the game's own logic once the dialog is confirmed. After the one-time keypress (settle-delayed via `spacePressSettleMs`=100ms), polls `ctx.inventory.IsEmpty()` every tick with no further action. Transitions to `goToBank` once empty. |
| `goToBank` (shared `GoToBankPhase`) | **Shared** | Constructed at `firemaking.ahk:328-335`: marker `(bankMarkerX, bankMarkerY) = (855, 1017)`, color `0x0000FF` (blue), tolerance 0, search padding 10px, reclick cooldown 6000ms, marker wait timeout 30000ms, bank-open anchor = `Images/deposit-default.png` at `(1327, 963)`, bank-open wait timeout 15000ms, poll key `"bankOpenPoll"` (100ms), **`nextPhaseName = "withdrawLogs"`** (for Firemaking the bank-open image is a pure signal, never clicked as deposit-all — contrast with Smelter/Smithing where the same image is clicked by the next phase). |
| `withdrawLogs` (`WithdrawLogsPhase`, `firemaking.ahk:133-201`) | **Bot-specific** (inlines its own withdraw-plan loop rather than sharing one with Smelter/Smithing's near-identical loop, per `ARCHITECTURE.md`) | Steps through `withdrawPlan` (built from `.ini`: `withdrawSlotCount=1`, `withdrawSlot1Index=1`, `withdrawSlot1Clicks=1` — **a trivial 1-slot/1-click plan**, confirming the `ARCHITECTURE.md` claim). Calls `Bank.WithdrawSlot(1, &x, &y)` → coordinate math only (`bankSlotFirstX=625, bankSlotFirstY=203, bankSlotPitchX=96, bankSlotW=72, bankSlotH=64`), then `ctx.clicker.ClickSettled(ctx, x, y, runMode)` once, gated by `withdrawClickIntervalMs` (100ms) between repeat clicks (irrelevant here since only 1 click). Once the plan is exhausted, applies a one-time `postWithdrawSettle` delay (`postWithdrawSettleDelayMs=600ms`), resets **all** per-cycle scratch state (fire marker flags/timestamps, bank marker flags/timestamps, `keyPressed`, withdraw-plan index/click-count), calls `ResetForNewCycle()` on every phase in `nextCyclePhases` (`[goToFire, burnLogs, goToBank, withdrawLogs]`), and transitions back to `goToFire`. |

| Settings | `indicatorSlot` | Inventory slot used to infer "full"/"empty" | 28 (last slot) | This is the **last slot filled last** — a reasonable choice for a bank-filled stack, but if logs are ever added to a different slot ordering (e.g. partial re-stack, other items in inventory) this single-slot heuristic could report "empty" (via `NotGate`) while logs actually remain in earlier slots, ending the burn loop early. See `ARCHITECTURE.md`'s note on the `emptyGate`/`fullGate` naming convention — Firemaking's `fullGate`/`NotGate(fullGate)` wiring at `firemaking.ahk:283-285` is confirmed correctly named (not the historical copy-paste bug). |

**Log type**: nothing in the `.ini` or code names a specific log (normal/oak/willow/maple/yew/magic) — there is no log-type string, item ID, or icon check anywhere in `firemaking.ahk` or the `.ini`. The bot is entirely log-type-agnostic by construction: it withdraws from a hardcoded bank slot index (`withdrawSlot1Index=1`) and waits for the dialog image + empty inventory, both of which are identical regardless of which log tier is actually in that slot. **Which log this is calibrated for is determined entirely by whatever item a human has manually placed in bank slot 1 and inventory before running** — this is a configuration/setup assumption, not something enforced or verified by the bot. Mechanically this is fine (all log tiers burn identically), but it means a misplaced item in bank slot 1 (e.g. after a bank reorganization) silently withdraws the wrong item with no content check.

## Known Risks & Edge Cases

**Scenario: Repeated fire-lighting at the same fixed ground spot (fire-tile blocking).**
**Current behavior**: `GoToFirePhase` always clicks the exact same static screen coordinate `(fireMarkerX, fireMarkerY) = (1532, 537)` (or the color-verified block found in a small padded region around it) on every single cycle, with zero movement, waypoint-stepping, or tile-offset logic anywhere in the phase, the `.ini`, or `WithdrawLogsPhase`'s cycle-reset. There is no `Walk`/`Waypoint` usage (that class is unused framework-wide per `ARCHITECTURE.md`), no randomized click offset in practice (`Humanizer` is `enabled=false`, so `Clicker.MoveTo`'s spatial jitter is always `(0,0)` — `Actions/Humanizer.ahk:18-23`), and no logic that reacts to "did a new fire actually ignite here, or is this tile already occupied by an existing fire."
**Risk/impact**: This is a **real, well-known OSRS Firemaking mechanic, not a hypothetical**: a lit fire occupies its ground tile until it burns out, so repeatedly clicking the identical tile/spot to light a *new* fire will fail once that tile still has an unburned fire on it — the click either does nothing (fire already there), triggers a "no space to light a fire here" game message, or (depending on click precision) selects an adjacent tile that may itself already be occupied by a fire from a few cycles ago, gradually forming a blocked cluster ("wall of fires") around the marker point. Since this bot's marker is a single fixed point with a fixed small search box (`fireMarkerSearchPaddingPx=30`), and the craft dialog (`craft-marker-1.png`) is the only "did this work" signal it waits for, a failed light (because the tile is occupied) most likely manifests as: the burn dialog never appears → `craftAnchor.WaitFor` times out at `craftMarkerWaitTimeoutMs` (15s) → `ctx.engine.Stop("Timed out waiting for burn dialog")`. In practice this means **the bot will likely self-stop within a few cycles of continuous running** once fires accumulate around the marker point, unless the marker's exact pixel happens to always land on ground that gets vacated by burn-out timing before the bot returns — which is fragile and not something the code guarantees. This is the single most important OSRS-specific gap in this bot.

**Scenario: Bank marker/anchor fails to be found (miscalibration).**
**Current behavior**: `GoToBankPhase` re-clicks the fixed `(bankMarkerX, bankMarkerY)` point every `bankMarkerReclickCooldownMs` (6s) until `ColorSearch.FindFilledBlock` matches `bankMarkerColor` (`0x0000FF`) within the padded region, or `bankMarkerWaitTimeoutMs` (30s) elapses, then stops the engine.
**Risk/impact**: Identical failure shape to the documented Smithing bug in `ARCHITECTURE.md` (wrong marker color silently never matches). The log symptom would be the same: repeated "Clicked bank marker" lines exactly `bankMarkerReclickCooldownMs` apart with no further progress, then a clean stop. Nothing in this bot's code guards against this beyond the generic timeout-stop; worth checking `bankMarkerColor=0x0000FF` against a live color-picker if this ever silently stops at `goToBank`.

**Scenario: Logs run out mid-inventory / inventory already empty when `burnLogs` is entered.**
**Current behavior**: `PressAndWaitEmptyPhase.Run` (`Core/SharedPhases.ahk:34-53`) presses `space` once, then polls `ctx.inventory.IsEmpty()` every tick with no further action, and transitions the moment it reports true. If the inventory is *already* empty at entry (e.g. a human manually started the bot with 0 logs, or a previous crash left state inconsistent), the phase still presses space once (harmless — the dialog either doesn't exist or is a no-op), then immediately sees `IsEmpty()==true` on the very next tick and moves on to `goToBank`. This is actually handled gracefully — no misfire, no infinite loop.
**Risk/impact**: Low — the shared phase's "poll until empty" design is naturally idempotent for an already-empty slot. The bigger risk is upstream: if `GoToFirePhase` successfully clicks a fire marker with **zero logs in inventory**, OSRS would likely show a "not enough logs"-type message (or no dialog at all) rather than the expected burn dialog — this surfaces as the same `craftAnchor.WaitFor` timeout described above, not a distinct code path.

**Scenario: Fire-lighting click blocked by another player standing on/near the spot (multiplayer world contention).**
**Current behavior**: No player-presence detection anywhere in this bot — `ColorSearch.FindFilledBlock` only looks for the green marker color, not for other players' overlays/models occupying the tile. If another player (or their fire) is standing on the exact marker pixel, the color match could fail outright (marker occluded) — falling into the same re-click-until-timeout path as any other "marker not found" case — or could succeed on a partially-visible sliver of the marker while the actual click lands on an occupied/blocked tile, producing a failed light indistinguishable (from this bot's perspective) from the tile-blocking scenario above.
**Risk/impact**: On a busy/crowded world or popular firemaking spot, this compounds directly with the fixed-spot fire-tile-blocking risk above — both funnel into the same "burn dialog never appears, timeout-stop" symptom, giving no direct signal to a human operator about *which* cause was responsible.

**Scenario: Wrong item withdrawn from bank slot 1 (no content verification).**
**Current behavior**: `WithdrawLogsPhase`/`Bank.WithdrawSlot` performs pure coordinate math and clicks — it never checks that the withdrawn item is actually the intended log type (there's no icon/color check on the resulting inventory slot).
**Risk/impact**: If bank slot 1 ever contains a different item (bank reorganized, tab changed, log type ran out of that specific slot), the bot will happily withdraw whatever is there and proceed into `goToFire`, where the burn dialog would simply never appear for a non-log item (same timeout-stop symptom again).

**Scenamo: `withdrawSlot1Clicks=1` and OSRS bank withdraw-quantity mode.**
**Current behavior**: The bot clicks bank slot 1 exactly once per cycle and assumes this withdraws a full inventory's worth of logs. OSRS banks have a withdraw-quantity mode (1/5/10/X/All) that is a **client-side UI toggle**, not something this bot sets or verifies before clicking.
**Risk/impact**: If the bank's withdraw mode is ever left on a low fixed quantity (e.g. "1") by a stray human click or a UI default, a single click withdraws only 1 log, not a full inventory — the bot would then proceed to `goToFire` with a near-empty inventory, burn almost nothing, and immediately timeout/stop or loop back to bank very quickly. Nothing in this bot sets/confirms "Withdraw All" mode before relying on 1 click; this is an implicit environmental assumption, not an enforced precondition.

## Anti-Ban / Human-Like Behavior Notes
- **`Humanizer` is constructed with `enabled=false`** (`firemaking.ahk:268`, `botHumanizer := Humanizer(false)`), matching every other bot in the framework per `ARCHITECTURE.md`. This means:
  - `Clicker.MoveTo`'s spatial click-offset jitter (`Humanizer.Offset`) always returns `(0,0)` — every click lands on the exact same pixel every time (the marker's detected center, or the fixed marker point itself while searching).
  - `Waiter`'s injected jitter function (`Humanizer.Jitter`) returns `baseMs` unchanged — every configured delay (`clickSettleMs`, `spacePressSettleMs`, poll intervals, `postWithdrawSettleDelayMs`) fires at its exact configured value, tick after tick, cycle after cycle.
  - `clickSettleJitterPercent=0` in the `.ini` is consistent with this (the value is inert either way, per `ARCHITECTURE.md`'s note that this plumbing is "fully inert but intentionally still present").
- **No randomization of the fire-lighting spot** — see Known Risks above; this is both an anti-ban gap (perfectly repeated pixel-identical clicks are a detectable pattern) and the root cause of the tile-blocking risk.
- **Poll intervals are fixed, not randomized**: `craftMarkerPollMs=100`, `bankOpenPollMs=100` — constant-cadence polling loops.
- **`runMode=1`** holds Ctrl during every click (OSRS "force run/force action" modifier) — this is a deliberate mechanical choice, not an anti-ban behavior.
- Net effect: this bot's on-screen behavior is currently fully deterministic and repetitive by design (same as its sibling bots) — the `Humanizer` scaffolding exists and is wired correctly, but is a no-op everywhere, consistent with the rest of the codebase.

## Bugs Found This Audit
- **`colorTolerance` (`.ini` Tunables, `auto-firemaking-v2.ini:19`) is declared in the schema (`firemaking.ahk:211`) and loaded, but never actually passed to either marker search.** Both `GoToFirePhase` (`firemaking.ahk:317-324`) and `GoToBankPhase` (`firemaking.ahk:328-335`) are constructed using `botConfig.Get("fireMarkerTolerance")`/`botConfig.Get("bankMarkerTolerance")` respectively (both hardcoded to `0` in the `.ini`), not `colorTolerance`. This key appears to be dead/vestigial config — changing it has zero effect on marker detection. Worth confirming whether this was intentional (leftover from an earlier single-tolerance design before per-marker tolerances were added) or a wiring oversight; either way it's currently misleading to a human tuning detection sensitivity.
- **No tile-relocation / same-spot mitigation for fire-lighting** — see the dedicated Known Risks scenario above. Not a code defect in the sense of a wrong line, but a structural gap: the bot has no concept of "this tile might be occupied," which is a first-class mechanic of the activity it automates.
- **No content verification after withdraw** (`WithdrawLogsPhase`, `firemaking.ahk:133-201`) — clicks bank slot 1 blind, trusts the `.ini`'s slot index is still correct, never checks the resulting inventory slot's appearance against an expected log icon/color.
- **No "already-full/already-banked" boot-state detection** — the engine always starts at `goToFire` (`firemaking.ahk:361`, `F5:: botEngine.Start("goToFire")`); there's no phase that checks inventory state at startup and redirects to `withdrawLogs` if starting from an empty inventory. (Documented as a known first-version limitation in the file's own header comment, `firemaking.ahk:7-9` — not a hidden bug, but worth surfacing here since it's a genuine operational gap.)

## Future Agent Development Roadmap
1. **Highest priority: add tile-relocation logic between fire-lighting attempts.** The current fixed-spot approach has no mechanism to detect or route around an already-occupied tile. Options worth exploring: (a) a small set of calibrated alternate marker points (e.g. 3-5 nearby tiles) that `GoToFirePhase` cycles through round-robin or on detected failure, similar in spirit to `Interfaces/Walk.ahk`'s waypoint list (currently unused framework-wide, per `ARCHITECTURE.md`) — this would be the natural class to extend for "click point N, then N+1 next cycle, wrapping around"; (b) on a `craftAnchor.WaitFor` timeout specifically (as opposed to other timeout causes), retry once against an alternate offset point before giving up and stopping, rather than stopping immediately. Either approach should be config-driven (new `.ini` keys for the alternate points), consistent with the framework's "nothing hardcoded" rule.
2. **Wire or remove the dead `colorTolerance` key** — either thread it into `fireMarkerTolerance`/`bankMarkerTolerance` as a shared default (with the per-marker keys as overrides), or delete it from the schema/`.ini` to avoid misleading a future tuner.
3. **Add a boot-time inventory check** that redirects straight to `goToBank`/`withdrawLogs` if the inventory is already empty when `F5` is pressed, removing the documented "must start with a full inventory" assumption.
4. **Consider a lightweight post-withdraw content check** (e.g. a `SlotGate`/color check on inventory slot 1 immediately after withdrawing) to catch a wrong-item withdrawal early rather than discovering it via a burn-dialog timeout several steps later — cheap to add given `Telemetry.ahk`'s existing gate primitives.
5. **If ever extended to a genuinely different bot variant** (e.g. a different log tier requiring a different bank tab/slot), follow the Smelter pattern already established in `ARCHITECTURE.md`: keep one `firemaking.ahk`, add a second `.ini` (e.g. `auto-firemaking-oak.ini`), and repoint/duplicate rather than parameterizing log type inside the code.
