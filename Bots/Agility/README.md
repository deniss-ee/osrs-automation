# Agility

## Overview
- Runs a full lap of an 8-obstacle OSRS Agility course by repeatedly finding the *current* obstacle's on-screen highlight overlay (a solid-colored block drawn over the clickable obstacle, e.g. by a client plugin/overlay), clicking its center, and advancing to the next obstacle in sequence, wrapping back to obstacle 1 after obstacle 8. The specific course isn't named in code/config comments (no course/obstacle-name strings anywhere), but the shape — 8 steps, one fall point after step 3, a Mark of Grace pickup step — is generic to any OSRS rooftop/ground agility course that a highlight overlay is drawn on top of. This bot does **not** read game text, XP drops, or the minimap — it is entirely a "find this color block, click it" loop.
- Also handles **Mark of Grace** pickups: every tick, before touching the current obstacle's coordinates, it does a whole-screen image search for `Images/mog-item.png`. If found, it clicks it and confirms the pickup via a small fixed pixel box (the inventory item-count area), then falls back to a bounded "dynamic search" mode for the current obstacle (since the detour to grab the mark likely moved the player off the obstacle's calibrated position).
- Start assumption: the player is already standing at the start of the course, current step is obstacle 1 (`ctx.Get("currentStep", 1)` default), inventory has free space (no bank/inventory-full handling exists in this bot at all — it just runs forever), and the client window is focused with the course visible at the exact calibrated positions in `Config/auto-agility.ini`.
- **Required calibration** (must be re-measured if resolution, client window size/position, zoom, or camera angle changes): every `[Step:N]` block's `x`/`y` (exact pixel **center** of that obstacle's highlight overlay, no search padding), `w`/`h` (exact pixel size of that overlay), and `color` (the overlay's own highlight color, 0xRRGGBB); the `[FallRecovery]` block's `x`/`y`/`w`/`h`/`color`; `[MarkOfGrace]`'s `imageW`/`imageH` (must match `Images/mog-item.png`'s real pixel dimensions) and `slotSignatureX`/`Y`/`W`/`H` (the item-count pixel box). None of these are searched with any positional tolerance outside of "dynamic mode" (see State Machine) — a moved/resized client window, different zoom level, or rotated camera silently breaks every one of these.

## Files
- Entry point: `Bots/Agility/agility.ahk`
- Config: `Config/auto-agility.ini`
- Log: `logs/auto-agility-v4-debug.log`
- Image asset: `Images/mog-item.png` (Mark of Grace reference image, captured against a `#00FF00` matte for `*TransARGB`-style transparent matching)

## State Machine
This bot has exactly **one** registered `Engine` phase, `"agility"` (`AgilityPhase`, `Bots/Agility/agility.ahk:104`) — there is no `Core/Phase`-level state machine spanning multiple named phases like other bots (no `goToX`/`bankX` phases). All state transitions happen *inside* `AgilityPhase.Run` via `ctx`-scratch integers, not via the `Engine`'s phase-name-returned mechanism. The phase always returns `"agility"` (never transitions to a different registered phase name) — from the `Engine`'s point of view this bot is a single infinite phase; the obstacle/course progress is tracked entirely in scratch state (`currentStep`, `checkedMarkForStep`, `dynamicSearchActive`) rather than as distinct `Phase` subclasses.

Effective sub-states within the one phase, per tick:

1. **Obstacle search** (`agility.ahk:140-206`): compute a search box for `STEPS[currentStep]` — either the step's own exact calibrated box (`fixed` mode) or a `dynamicSearchWidthPx x dynamicSearchHeightPx` window centered on the step's calibrated position at a smaller fixed block size (`dynamic` mode, entered after a Mark of Grace detour). `ColorSearch.FindFilledBlock` searches for the step's own unique highlight color within that box, biased toward the step's known position via the `refX`/`refY` steering parameters.
   - **Found** → proceed to Mark of Grace check (state 2).
   - **Not found** → check fall recovery (state 4) if this is the step right after the configured fall point; otherwise just wait (`ctx.waiter.After(..., step["pollKey"])`) and re-tick, still in obstacle-search mode. No state change, no timeout progress reset — `ResetPhaseTimer` is NOT called on a "not found" tick, so the 30s `phaseTimeoutAgility` clock only pauses on genuine clicks/progress (fall-recovery click, obstacle click), keeping "obstacle never appears" a real terminal failure.
2. **Mark of Grace check** (`agility.ahk:211-275`), only once per step (latched by `checkedMarkForStep`, only evaluated once the current step's own highlight has actually been found — i.e. "we've arrived", not mid-walk): searches the whole screen for `mog-item.png`. If found: snapshots the item-count box (`SlotSignature.Snapshot()`), clicks the mark (with a configured Y offset), then polls the item-count box for a change up to `gracePickupTimeoutMs`. On confirmed change, loops again (another mark may be visible) after a settle delay; on timeout, gives up on marks for this step. Either way (found-and-clicked or not found at all... actually only set on the *found* branch reaching completion — see Bugs section), sets `dynamicSearchActive=true` if a mark was ever clicked this step, and re-ticks so the *next* tick re-searches the obstacle fresh instead of clicking a possibly-stale `(cx,cy)`.
3. **Obstacle click** (`agility.ahk:277-292`): clicks the `(cx,cy)` found in state 1 (only reached if no mark detour forced a re-search this tick), resets the phase timeout, advances `currentStep` (wrapping `steps.Length → 1`), resets `checkedMarkForStep` and `dynamicSearchActive` to `false` for the new step, then settles (`stepSearchDelay`) before the next tick.
4. **Fall recovery** (`agility.ahk:176-206`), only ever checked when `currentStep = fallRecoveryBlock["afterStep"] + 1` AND that step's own highlight was NOT found this tick: searches for the configured fall-recovery block (a fixed "back on solid ground" marker with its own w/h/x/y/color). If found: waits `fallRecoveryDelayMs`, clicks it, resets the phase timer, **hard-resets `currentStep` to 1** (does not resume from the step before the fall — restarts the whole lap), clears `checkedMarkForStep`/`dynamicSearchActive`, and re-ticks. `[FallRecovery] enabled=0` disables this branch entirely (`fallRecoveryBlock := ""` at wiring time, `agility.ahk:387-397`).

There is no "lap complete" event/counter — completing 8 obstacles just wraps `currentStep` back to 1 silently (`agility.ahk:281-283`); nothing logs or counts full laps.

`Config/auto-agility.ini`, all keys validated fail-fast by `Config.Load()` (missing keys = startup error listing all of them at once).

| Meta | `schemaVersion` | Config format version tag, unused at runtime | `1` | Cosmetic only |
| Settings | `runMode` | Hold Ctrl (force-run) during every click | `1` | `0` = normal walk clicks instead of force-run; slower course traversal, more time exposed mid-obstacle |
| Settings | `stepCount` | Number of `[Step:N]` sections/obstacles in the course | `8` | Must exactly match the number of `[Step:N]` blocks present; mismatch = either `IniRead` throws on a missing section, or trailing steps are silently ignored |

| Tunables | `colorTolerance` | Per-channel +/- tolerance matching each step's/fall-block's highlight color | `10` | Too low = misses the block on lighting/anti-aliasing variance; too high = false-positive matches against scenery, especially risky for common colors like step 5's pure green (`0x00FF00`) or step 8's yellow (shared with the fall-recovery block's color, see Bugs) |

| Step:N | `color` | That obstacle's unique highlight color, `0xRRGGBB` | per-step (should be unique per step — see Overview and Bugs) | A duplicate color across two steps breaks the "re-find this exact step anywhere on screen by color alone" assumption used after a Mark of Grace detour |
| Step:N | `stepSearchPollNMs` | Poll interval while waiting for step N's highlight | per-step, 800–2800 | Too low = wasted `PixelSearch` calls (perf cost); too high = added latency picking up an obstacle that's actually already available |
| FallRecovery | `enabled` | 1 = check for fall recovery, 0 = disabled | `1` | `0` means any actual fall is completely unhandled (see Known Risks) |
| FallRecovery | `afterStep` | The step number after which a fall is known to happen | `3` | Wrong value = fall recovery checked at the wrong point in the course, likely never firing when a real fall happens after a *different* step |
| FallRecovery | `w`, `h`, `x`, `y`, `color` | The "back on solid ground" marker's exact size/position/color | calibrated | Same failure mode as a `[Step:N]` miscalibration — silently never found |

| MarkOfGrace | `mogShadeTolerance` | `ImageSearch` shade-variation tolerance (0-255) | `20` | Too low = misses the mark under lighting/animation variance; too high = false positives |
| MarkOfGrace | `graceClickOffsetY` | Y pixel offset applied before clicking the found mark | `6` | Miscalibration = click lands slightly off the mark's actual clickable point |
| MarkOfGrace | `gracePrePickupDelayMs` | Pause before checking for a mark, once per step | `100` | Small guard against searching in the exact instant the obstacle highlight was found — not a real settle window |
| MarkOfGrace | `slotSignatureX/Y/W/H` | Fixed pixel box (item-count area) watched for a pickup-confirming change | calibrated | Wrong box = `SlotSignature.HasChanged` never fires (or always fires on noise), breaking pickup confirmation either direction |
| MarkOfGrace | `gracePickupTimeoutMs` | Max wait for the item-count box to change after clicking a mark | `2800` | Too short = real pickups get treated as "timed out" (see Bugs — no functional difference today, but wrong logging/state) |

| MarkOfGrace | `dynamicSearchWidthPx`, `dynamicSearchHeightPx` | Bounded search window size (centered on step's calibrated pos) in dynamic mode | `1024`, `576` | Too small = misses the obstacle if the detour moved the player further than expected; too large = approaches whole-screen search cost for common colors |

## Known Risks & Edge Cases

- **Camera orientation: zero handling, highest-severity risk for this bot.** Every single obstacle coordinate (`[Step:N] x/y/w/h`), the fall-recovery block, and the Mark of Grace slot-signature box are absolute screen pixel positions calibrated once and hardcoded in the `.ini`. There is no compass/camera-angle check, no camera-reset step (no "look north" click, no middle-mouse recenter, no minimap click), and no code anywhere in `agility.ahk` that reads or resets camera state. → **Risk**: OSRS's camera auto-rotates in some client configurations, and manual bumps (arrow keys, middle-mouse drag, alt+scroll zoom, a minimap click that recenters/rotates the view) are common incidental side effects of nearby human input or even certain obstacle animations. If the camera drifts even slightly between calibration time and runtime, every one of the 8 obstacles' highlight blocks physically moves on screen relative to the calibrated `x/y` — the fixed-box search (non-dynamic mode) will simply never find them, since no positional tolerance exists outside of "dynamic mode," and dynamic mode is *only* entered after a Mark of Grace detour, never after camera drift. The bot has no way to distinguish "camera rotated" from "obstacle genuinely isn't there yet" — both look identical (search comes back empty) and both just wait on the poll timer, eventually hitting `phaseTimeoutAgility` and stopping the whole engine.
- **Obstacle/skill-check failure ("falling off") is only handled for ONE specific step, and only as a positional heuristic, not a real fail-state detector.** OSRS agility courses have a real per-obstacle fail chance (especially at higher obstacles or lower levels) that sends the player to a different location (often a lower course level) and interrupts the expected step sequence. This bot's only concession to that is the `[FallRecovery]` block, hardwired to fire only when `currentStep = afterStep + 1` (i.e. only a fall after step 3, landing near a specific recovery marker). → **Current behavior**: a fall after *any other* step (1, 2, 4, 5, 6, 7, or 8) is completely undetected — the bot just keeps searching for that step's highlight in the wrong location (the player is now standing somewhere the overlay never renders), waits out its poll interval repeatedly, and eventually trips `phaseTimeoutAgility` (30s) and stops the entire engine. → **Risk**: this is a real, expected OSRS mechanic (not a rare edge case) on a course with any fail-capable obstacle, and it will fully halt unattended botting the first time it happens on an unguarded step.
- **Fall recovery, even where implemented, restarts the whole lap from step 1 rather than resuming after the actual fall point** (`ctx.Set("currentStep", 1)`, `agility.ahk:196`) — functionally safe (never gets stuck) but wastes an entire lap's worth of already-completed obstacles every time it fires.
- **No detection for another player/NPC obstructing an obstacle's clickbox.** Detection is a solid-color-block search (`ColorSearch.FindFilledBlock`, which requires the found block to pass a 75%-of-size verification), not an image or hitbox check. → If another player's model, a random-event NPC, or their own overlay physically occludes part or all of the highlight block, `VerifyBlock`'s cross-check can fail even though the obstacle itself is still logically there — this looks identical to "obstacle not found yet" and just waits on the poll timer. No fallback search radius, no "try again with a smaller/offset box."
- **No handling for course congestion in general** — a crowded course (common on popular worlds) has no dedicated logic; it inherits the same "not found → wait → eventually timeout" behavior as camera drift or occlusion. All three failure modes are indistinguishable from the bot's point of view and produce the same symptom (repeated "Waiting for step N" log lines with no progress).
- **No random-event handling of any kind.** No detection for a random-event NPC spawning, a "Talk to" dialog, a teleport-away minigame, or a butler/genie appearing — the bot has no screen for anything other than the specific step colors, the Mark of Grace image, and the fall-recovery color. A random event visually altering the screen (its own overlay, a dialog box, a teleport moving the player entirely off the course) is handled exactly like every other "unexpected screen state": treated as "step not found," waited out, eventually timed out.
- **Lost window focus mid-obstacle**: guarded correctly — `Run(ctx)`'s first line (`agility.ahk:134-135`) checks `ctx.windowFocus.IsActive()` and returns early without searching/clicking if the client isn't focused, consistent with every other bot in the framework. No progress is lost, but no phase-timer reset happens either while unfocused, so an extended alt-tab could itself trip `phaseTimeoutAgility` even though nothing is actually wrong.
- **Stale scratch state across "laps"**: `ResetForNewCycle()` (`agility.ahk:129-131`) is a deliberate no-op — `currentStep` intentionally persists indefinitely (this bot has no cycle boundary the way bank-cycle bots do). This is fine as designed, but means there is no lap counter, no "N laps completed" log/metric, and nothing resets between what a human would call one full course lap and the next — worth keeping in mind if a future agent wants to add lap-based logic (XP/hour estimation, stopping after N laps, etc.) since there's currently no hook for it.
- **Whole-screen Mark of Grace search runs every tick until latched per step** (`this._mogAnchor.Find` inside a `loop` at `agility.ahk:214-264`, guarded only by `checkedMarkForStep`) — an `ImageSearch` over the full screen region (`mogRegion` is `0,0` to `A_ScreenWidth,A_ScreenHeight`, `agility.ahk:367`) is comparatively expensive; this is fine once-per-step but would be a perf concern if the latch logic were ever changed to re-check more often.

## Anti-Ban / Human-Like Behavior Notes
- `Humanizer` is constructed with `enabled=false` (`agility.ahk:347`, `botHumanizer := Humanizer(false)`), matching every other bot in the framework — this makes `Humanizer.Offset` (spatial click jitter) and `Humanizer.Jitter` (temporal delay jitter) both hard no-ops. `clickSettleJitterPercent=0` in the `.ini` is consistent with this but currently has no effect either way since jitter is globally disabled at the object level, not just zeroed in config.
- All click positions are otherwise exact: obstacle clicks go to the verified block's own center (clamped to the search region), Mark of Grace clicks go to the image's found center plus a fixed `graceClickOffsetY`, fall-recovery clicks go to the verified fall-block's center. No randomized offset is applied to any of these today.
- Poll intervals (`stepSearchPollNMs`, `graceConfirmPollMs`, etc.) are per-obstacle-tuned fixed values, not randomized — same "config-driven but not jittered" pattern as every other bot's `Waiter`/`TimingProfile` usage, since jitter is universally disabled.
- `runMode=1` holds Ctrl during clicks (OSRS "force-run" click modifier) for every click this bot makes — a deliberate, consistent choice, not obviously bot-like on its own, but 100% consistent click cadence/spacing (no jitter) and 100% consistent click-to-exact-pixel-center behavior are both classic automation signatures if this course is ever scrutinized.

## Bugs Found This Audit
- **`agility.ahk:243` sets `dynamicSearchActive := true` unconditionally inside the Mark-of-Grace `loop`, on every iteration — including the very first check where `this._mogAnchor.Find` returns false and the loop `break`s immediately at line 218 without ever reaching line 243.** Re-reading the control flow: line 216's `if (!this._mogAnchor.Find(&mx, &my))` breaks *before* line 243, so `dynamicSearchActive` is only set when a mark actually was found and clicked (at least once) — this part is actually correct. However, note the comment at lines 268-270 justifies re-ticking on `dynamicSearchActive` as "a loot detour happened," which is accurate — no bug here after closer trace, but the logic is easy to misread on a first pass; flagging for whoever edits this next since the nesting (search loop inside a per-step latch) is the densest part of the file.
- **Fall recovery and a real `[Step:N]` color collision risk**: Step 8's highlight color is `0xFFFF00` (pure yellow, `auto-agility.ini:109`) and the `[FallRecovery]` block's color is also `0xFFFF00` (`auto-agility.ini:134`) — identical. Fall recovery is only ever searched while `currentStep = 4` (i.e. `afterStep(3) + 1`), and step 8's own search only runs while `currentStep = 8`, so in practice these two searches never run concurrently with the current `afterStep=3` config — but this is a fragile coincidence, not an enforced invariant. If `afterStep` is ever reconfigured (e.g. to make fall recovery trigger after step 7, checking during step 8), the fall-recovery search and step 8's own obstacle search would use the exact same color, position notwithstanding — a future maintainer changing `afterStep` without noticing this color reuse could get cross-detection between "step 8's highlight" and "the fall recovery marker."
- **No lap counter / no completion telemetry**: functionally harmless, but there is no log line, counter, or `ctx` scratch value marking "one full lap done" anywhere — `currentStep` just silently wraps (`agility.ahk:281-283`). Anyone trying to measure obstacles/hour or laps/hour from the log today has to infer it by counting "Found step 1" lines.
- **`phaseTimeoutAgility` (30000ms) is a single shared timeout across all 8 obstacles plus fall recovery plus Mark of Grace detours**, despite the steps' own poll intervals varying from 800ms to 2800ms and Mark of Grace pickup adding up to `gracePickupTimeoutMs` (2800ms) more per mark, potentially more than once per step (the mark-pickup `loop` repeats "Loop again - another mark may be visible" after every confirmed pickup, uncapped in iteration count). A step with an unusually long real animation, stacked with one or two Mark of Grace pickups in the same spot, could plausibly approach or exceed 30s of genuine (non-stuck) progress before ever calling `ResetPhaseTimer` again — worth checking against real course timing rather than assuming the current value has headroom.

## Future Agent Development Roadmap
- **Add a camera-reset step before starting the course (and ideally before every lap or every N obstacles)**: e.g. click the compass to reset to north-facing, or send a fixed camera-recenter keybind, before the first obstacle search of each run. This is the single highest-value fix given this bot's total reliance on absolute screen coordinates — every other risk in this file is secondary to camera drift.
- **Add a distinguishing "stuck vs. camera-drifted vs. fallen" signal.** Today all three look identical (search returns false, wait, eventually timeout). Consider: after N consecutive poll misses on the same step (configurable, well under `phaseTimeoutAgility`), trigger a broader/whole-screen search for that step's color (same idea as the existing Mark-of-Grace dynamic-search fallback) before assuming a stuck/fallen state — this would also incidentally help with minor camera drift without requiring a full camera-reset mechanism.
- **Generalize fall recovery to more than one step.** Currently `[FallRecovery]` supports exactly one `afterStep`/marker pair. A real course likely has more than one obstacle with a nonzero fail chance. Consider an array shape (`fallRecoveryCount` + `[FallRecovery:N]` sections, mirroring the existing `[Step:N]` pattern) so each fail-capable obstacle gets its own recovery marker, rather than only the one currently hardwired via `afterStep=3`.
- **Make fall recovery resume from the recovered position instead of hard-resetting to step 1**, if the recovery marker's location has a knowable relationship to a specific step in the course (may require a second calibrated marker or an intermediate "walk back to the course" waypoint sequence, similar to `Interfaces/Walk.ahk`'s `Waypoint` shape — currently unused by any bot, but this is exactly the kind of multi-step traversal it was built for).
- **Add a lap counter and log it** (`ctx.Set("lapsCompleted", ...)`, incremented whenever `currentStep` wraps from `steps.Length` back to `1`) — cheap to add, immediately useful for measuring throughput and for a future "stop after N laps" feature.
- **Consider a random-event or "unexpected overlay" tripwire**: e.g. if `phaseTimeoutAgility` fires unusually often in the log, or a dedicated periodic check for a known random-event indicator (if one can be calibrated) that pauses the bot rather than letting it grind uselessly against a screen it can't interpret.
- **Reconcile the Step 8 / FallRecovery color collision** noted in Bugs — either pick a visually distinct fall-recovery marker color, or add an explicit code comment/assertion warning future config editors not to let `afterStep + 1`'s step color collide with the fall-recovery color.
- **Consider whether `SlotSignature` (raw pixel-box snapshot/diff, used here for Mark-of-Grace pickup confirmation) should be replaced with `Telemetry.ahk`'s `SlotSignatureGate`** if this bot's `Inventory` interface is ever wired up (it currently isn't — `ctx.inventory` is never set for this bot) — `SlotSignatureGate` is the more general "baseline snapshot, detect any change" gate already used by Smelter, whereas `SlotSignature` here is a bespoke raw-coordinate version built because this bot never constructs an `Inventory`/slot-indexed layout at all. Not a bug, just worth knowing both exist and why this bot uses the standalone one.
