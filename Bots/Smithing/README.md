# Smithing

## Overview
- Automates smithing bars into items at an anvil in OSRS: walk to the anvil, open the smithing interface, smith the entire inventory of bars via a single "smith all" confirmation, walk to the bank, deposit everything, withdraw a fresh stack of bars, and repeat. One full loop = one inventory of bars turned into finished items and banked (implicitly — this bot only deposits/withdraws; it never verifies the smithed *products* get sold or handled beyond being cleared from the inventory on the next deposit).
- Start location / setup assumptions: character standing near the anvil with the inventory **already full of bars** (per the file header comment: "First version: assumes F5 is pressed with a full inventory of bars already in hand"). The withdraw plan in `depositAndWithdraw` does refill the inventory from the bank each cycle, but the very first cycle after pressing F5 depends on the anvil marker and craft dialog already being reachable/visible with bars on hand — it does not check inventory state before starting.
- Required calibration (all fixed pixel coordinates/colors, screen-resolution- and client-layout-dependent): anvil marker position/color/size, smith-dialog image anchor position, bank marker position/color/size, bank-open (deposit) image anchor position, bank slot layout (for withdraw), and the shared inventory pixel grid (hardcoded in `smithing.ahk`, not in the `.ini`).

## State Machine

4 phases, cycle: `goToAnvil -> smith -> goToBank -> depositAndWithdraw -> goToAnvil`

1. **`goToAnvil`** (bot-specific class `GoToAnvilPhase`, `Bots/Smithing/smithing.ahk:48-121`)
   - Detection: `ColorSearch.FindFilledBlock` searches a padded region around the calibrated `(anvilMarkerX, anvilMarkerY)` point for a solid `anvilMarkerW x anvilMarkerH` block of `anvilMarkerColor` (magenta, `0xFF00FF`) within `anvilMarkerTolerance` (0 = exact match).
   - Click logic: if not found, re-clicks the fixed marker point on a `anvilMarkerReclickCooldownMs` (6000ms) cadence until found or `anvilMarkerWaitTimeoutMs` (30000ms) elapses (then `ctx.engine.Stop(...)` cleanly — never throws/loops forever). Once found, clicks the *found* block's own center (not the raw calibrated point) exactly once, gated by a `anvilMarkerClicked` scratch flag.
   - After clicking, waits (`craftAnchor.WaitFor`) for `craft-marker-2.png` — the "smith X" dialog image — to appear, polling at `craftMarkerPollMs` (100ms) up to `craftMarkerWaitTimeoutMs` (15000ms). Times out to a clean stop if the dialog never appears.
   - Transition: once the dialog image is confirmed visible, returns `"smith"`.
   - This phase is structurally identical to `GoToBankPhase` in `Core/SharedPhases.ahk` (fixed marker + reclick cooldown + image-wait) but is **not** the shared class — ARCHITECTURE.md notes `GoToAnvilPhase`/`GoToFurnacePhase`/`GoToFirePhase` were deliberately left unshared because their scratch-key names (`anvilMarkerWaitStartedAt` etc.) are hardcoded per-bot.

2. **`smith`** — the shared `PressAndWaitEmptyPhase` (`Core/SharedPhases.ahk:21-54`), constructed at `Bots/Smithing/smithing.ahk:354` as `PressAndWaitEmptyPhase("smith", botKeyAction, "space", "spacePressSettle", "goToBank")`. No Smithing-specific code exists for this phase — it presses `[space]` once (confirms the "smith X" dialog, which in-game triggers "smith all" of that bar type), waits `spacePressSettleMs` (100ms), then polls `ctx.inventory.IsEmpty()` every tick until true, then transitions to `"goToBank"`. See ARCHITECTURE.md for the general shape.
   - **In OSRS terms**: pressing space confirms the smithing interface's currently-highlighted/default item choice and (per the in-game "smith X" quantity prompt convention) attempts to smith the whole stack of the loaded bar type in one action chain, one item click cycle handled entirely client-side by the game after the single space press — this bot does not click through the smithing interface's item-selection grid, does not click "All" explicitly, and does not send a quantity. It relies entirely on whatever the interface's default selection is when space is pressed. See Known Risks for what happens if that default isn't what's intended.

3. **`goToBank`** — the shared `GoToBankPhase` (`Core/SharedPhases.ahk:66-140`), constructed at `Bots/Smithing/smithing.ahk:356-363`. Verifies the fixed-point blue bank marker (`bankMarkerColor`), clicks it (reclick cooldown `bankMarkerReclickCooldownMs`, timeout `bankMarkerWaitTimeoutMs`), then waits for `deposit-default.png` (the bank-open signal) via `bankOpenAnchor`, then transitions to `"depositAndWithdraw"`. No Smithing-specific code.

4. **`depositAndWithdraw`** (bot-specific class `DepositAndWithdrawPhase`, `Bots/Smithing/smithing.ahk:135-221`)
   - Step 1: waits for `deposit-default.png` again (re-verifies bank interface is actually open — same anchor `GoToBankPhase` already waited for), then clicks its own freshly-found center as "deposit all," gated by a `depositClicked` flag.
   - Step 2: steps through the withdraw plan (`Config` array of `{slotIndex, clicks}` built from `.ini` `withdrawSlotCount`/`withdrawSlot<i>Index`/`withdrawSlot<i>Clicks`), clicking `Bank.WithdrawSlot`'s computed coordinates per entry, respecting `withdrawClickIntervalMs` (100ms) between repeat clicks on the same slot, advancing `withdrawPlanIndex`/`withdrawClicksDone` scratch state until the whole plan is exhausted.
   - Step 3: applies a one-time `postWithdrawSettle` delay (100ms) — camera/character settle time before the anvil marker is searched again — then resets **every** per-cycle scratch flag (anvil marker wait/click state, `keyPressed`, bank marker wait/click state, deposit/withdraw state) and calls `ResetForNewCycle()` on all phases in `nextCyclePhases`, then transitions back to `"goToAnvil"`.
   - This phase's shape is closer to Smelter's `DepositAndWithdrawPhase` (own deposit-all pre-step + withdraw loop) than to Firemaking's plain withdraw phase — per ARCHITECTURE.md, this is why it isn't unified into a shared class despite the similarity.

### `bankMarkerColor` bug status — CONFIRMED FIXED

ARCHITECTURE.md documents a historical bug: `bankMarkerColor` was originally `0xFF00FF` (magenta, copy-pasted from the anvil marker directly above it in the `.ini`), which is visually identical to the anvil's own marker color, causing `GoToBankPhase` to search for the wrong color at the bank marker's location and never find it — silently re-clicking the bank-marker point forever, timing out at `bankMarkerWaitTimeoutMs` with nothing ever deposited or withdrawn.

Reading the current `Config/auto-smithing-v2.ini` directly (line 68): `bankMarkerColor=0x0000FF` — this **is** blue, distinct from `anvilMarkerColor=0xFF00FF` (magenta, line 29). **The bug is fixed in the current config.** No further action needed here, but this key is worth a quick visual sanity-check after any future manual `.ini` edit near this section, precisely because the two color keys sit close together in the file and are easy to transpose again by copy-paste.

## Known Risks & Edge Cases

- **Anvil occupied by another player** → **Current behavior**: `GoToAnvilPhase` only checks for the fixed-point marker color/block and the "smith X" dialog image — it has no concept of "another player is standing at/using this anvil." If the marker itself is still visible (e.g. the anvil object marker isn't blocked by another player model), the bot will click it and wait for the dialog; if OSRS doesn't open the smithing interface because the anvil is busy, the bot will simply time out at `craftMarkerWaitTimeoutMs` (15000ms) and stop cleanly. → **Risk/impact**: no retry/backoff logic for a temporarily-busy anvil — the bot stops entirely rather than waiting for the anvil to free up, requiring manual restart even though the situation is transient.

- **Bars run out mid-smith (or fewer bars than expected)** → **Current behavior**: `smith` phase (`PressAndWaitEmptyPhase`) presses space once, then polls `ctx.inventory.IsEmpty()` (via `indicatorSlot=26` and `SlotGate`/`NotGate`) with **no timeout of its own** — the only ceiling is the outer `phaseTimeoutAnvil` (180000ms) applied at the Engine level via `AddPhase(botSmithPhase, botConfig.Get("phaseTimeoutAnvil"))`. If bars run out mid-smith (e.g. the "smith X" quantity prompt was actually smithing fewer items than a full inventory, or the player only had a partial stack), the game stops smithing on its own once no bars remain to smith, and slot 26 (last-filled slot per the comment "last slot filled last") should go empty and this still resolves correctly *if the withdraw plan actually fills that slot every cycle*. **However**, if slot 26 for some reason is never filled at all in a given cycle (e.g. an interrupted withdraw, or a partial bar stack from a previous under-filled withdraw — see below), `IsEmpty()` on that slot could report a false "already empty" and the phase would immediately (and wrongly) declare smithing done. → **Risk/impact**: this is a hard dependency on slot 26 both being filled every cycle AND correctly reflecting completion — a partial/failed withdraw silently changes the meaning of "empty," with no cross-check against the actual bar count.

- **Multi-bar items (items requiring more than one bar per smith, e.g. platebodies needing 5 bars)** → **Current behavior**: this bot does not click through the smithing interface's item-selection grid at all — it presses `[space]` once, relying entirely on the interface's default/last-used selection and OSRS's own "smith all of stack" behavior for whatever item is currently selected. It has no logic to select a *specific* item (e.g. "always smith platebodies" vs. "always smith daggers") and no logic to handle the possibility that a multi-bar item can't be completed with the bars on hand (e.g. 3 bars left, item needs 5) — OSRS itself would simply smith as many complete items as the bar count allows, then stop with leftover bars in the slot. → **Risk/impact**: if leftover, non-zero, sub-threshold bars remain in slot 26 (or the tracked indicator slot) after the game's own auto-stop, `IsEmpty()` never becomes true, and the phase would hang until `phaseTimeoutAnvil` (3 minutes) force-stops it — this is a real, plausible failure mode for any multi-bar item whose bar count doesn't divide evenly into a full inventory of bars.

- **Smithing interface requires an explicit item-selection click (not just space)** → **Current behavior**: only `[space]` is pressed (`PressAndWaitEmptyPhase`'s `_key` argument is `"space"`, wired at `smithing.ahk:354`). If the in-game smithing interface doesn't have the intended item pre-selected/defaulted (e.g. after a client update changes default selection behavior, or the player is smithing a bar type for the first time and no "last selection" exists yet), pressing space alone may confirm the wrong item, or do nothing if no item is highlighted. → **Risk/impact**: this bot has zero interface-navigation logic (no mouse clicks inside the smithing dialog's item grid) — it is only safe to run for a bar/item combination where the game already defaults to the correct item on dialog-open. This is a real, silent risk: it would smith the wrong item with no error, since the phase only checks "did the inventory become empty," not "did the RIGHT item get produced."

- **Withdraw plan withdraws only 1 slot, 1 click** (`withdrawSlot1Index=1`, `withdrawSlot1Clicks=1`) → **Current behavior**: a single click on bank slot 1. → **Risk/impact**: in standard OSRS bank UI, a single left-click on a stackable item withdraws either 1 unit or the bank's currently-configured default withdraw quantity/mode (varies by client withdraw-mode setting: 1/5/10/X/All). If the bank isn't in "withdraw-all" mode, one click could withdraw far fewer bars than a full 28-slot inventory needs, leaving most of the inventory empty after the withdraw step — `postWithdrawSettleDelayMs` then hands off to `goToAnvil` regardless of how many bars were actually obtained, with no check that the inventory is actually full/near-full before smithing starts again. This is analogous to Firemaking's "trivial 1-slot/1-click plan" per ARCHITECTURE.md, but there logs are typically non-stacking-quantity-sensitive in the same way bars are for a full-inventory smithing cycle — worth explicitly verifying the bank's configured withdraw mode matches the assumption of "1 click = enough bars," or increasing `withdrawSlot1Clicks`/switching the bank to withdraw-all as a fix if this turns out to under-withdraw live.

- **No hammer withdrawn** → **Current behavior**: the withdraw plan only withdraws from bank slot 1 (presumably the bar stack). No second withdraw entry exists for a hammer. → **Risk/impact**: this matches standard OSRS practice (a hammer is not consumed and is typically kept in the inventory/never needs re-withdrawing, or many accounts keep a permanent hammer via achievement diary perks) — **not a bug**, but worth flagging explicitly: if the hammer is ever accidentally dropped/banked, this bot has no mechanism to detect a missing hammer or re-acquire one, and would presumably fail silently at the `smith` phase (dialog might not even open, or would open with no way to smith), likely manifesting as a `craftMarkerWaitTimeoutMs` stop.

- **`anvilMarkerTolerance=0` / `bankMarkerTolerance=0`** (exact color match only) → **Current behavior**: both marker searches require a pixel-perfect match to the calibrated color, unlike the general-purpose `colorTolerance=20` defined but unused for these two specific checks. → **Risk/impact**: any anti-aliasing, screen scaling, or client theme/rendering change could break marker detection entirely with zero tolerance for drift — normally this manifests as the reclick-cooldown symptom (ARCHITECTURE.md's "two 'Clicked X marker' lines exactly `reclickCooldownMs` apart with nothing after") pointing at a detection failure rather than a logic bug.

- **No verification that deposited/withdrawn items are correct** → **Current behavior**: `DepositAndWithdrawPhase` clicks "deposit all" and then blindly executes the withdraw plan by slot index and click count — there is no color/image check confirming slot 1 actually still contains bars (vs. having been moved/sold/reorganized in the bank tab), nor any check that inventory is non-empty and matches the bar item after withdrawing. → **Risk/impact**: if the bank tab layout changes (item moved to a different slot, e.g. by an unrelated withdrawal of some other item elsewhere shifting tab order), this bot would silently withdraw whatever is now in slot 1, which may not be bars at all, then proceed to click at the anvil and press space against a full inventory of the wrong item.

## Anti-Ban / Human-Like Behavior Notes

- `Humanizer` is constructed with `enabled=false` (`smithing.ahk:288`) — identical to every other bot in this framework. This means `Humanizer.Offset` (spatial click jitter) and `Humanizer.Jitter` (delay jitter) are both pure no-ops: clicks land exactly at calculated coordinates every time, and every `Waiter.After` delay is exactly its configured `baseMs` with zero randomization, despite `clickSettleJitterPercent` existing as a nonzero-capable `.ini` key.
- Per ARCHITECTURE.md, this is a deliberate, standing decision across the whole framework, not an oversight specific to Smithing — the humanization plumbing is intentionally kept in place (for potential future re-enabling) but inert.
- Poll intervals (`craftMarkerPollMs=100`, `bankOpenPollMs=100`) and click-settle delays (`clickSettleMs=100`, `withdrawClickIntervalMs=100`) are all fixed, non-randomized values.
- `runMode=1` means every click is wrapped in a held Ctrl (force-run) — this is a gameplay behavior (forces the character to run), not an anti-detection behavior, and has no relation to humanization.
- **Net effect**: this bot's click timing and positioning are currently fully deterministic and repeatable — every cycle clicks the exact same pixels with the exact same delays, which is the opposite of human-like variance, consistent with every other bot in this framework today.

## Bugs Found This Audit

- **`bankMarkerColor` historical bug: CONFIRMED FIXED, does not recur.** Current `Config/auto-smithing-v2.ini:68` reads `bankMarkerColor=0x0000FF` (blue), correctly distinct from `anvilMarkerColor=0xFF00FF` (magenta) at line 29. No code or config change needed.
- **`anvilMarkerTolerance=0` and `bankMarkerTolerance=0`** (`Config/auto-smithing-v2.ini:30,69`) — both use exact-match tolerance while a general `colorTolerance=20` exists and is used elsewhere (e.g. `SlotGate`/`fullGate` construction at `smithing.ahk:303`). Not necessarily a bug (live-verified to work per CURRENT_STATE.md), but zero margin for rendering drift is worth flagging — if this bot ever starts exhibiting the "repeated reclick, no further progress" symptom ARCHITECTURE.md describes, check these two tolerance values first, not just the color values.
- **No inventory-full/bar-count verification before/after withdraw** (`Bots/Smithing/smithing.ahk:173-195`, the withdraw loop) — the phase advances strictly by configured click counts with no check that the inventory actually received the expected number of bars. Given `withdrawSlot1Clicks=1`, this is a real latent risk if the bank's withdraw-quantity mode isn't "All" (see Known Risks above) — this is a design gap, not a coding bug, but it's the single most likely cause of a future live failure report ("bot smiths a half-empty inventory") if the bank withdraw mode is ever changed or wasn't set correctly during original calibration.
- **No check that `smith` produces the intended item** — `PressAndWaitEmptyPhase` only checks "inventory became empty," never "the produced item is correct." Combined with only pressing `[space]` and never clicking a specific item in the smithing grid, this bot structurally cannot detect "smithed the wrong thing" as a failure mode (see Known Risks). This is inherent to the shared phase's generic contract, not something introduced by Smithing specifically, but Smithing is the bot most exposed to it since the anvil's item-selection UI has many more choices than Firemaking's single "light log" action.

## Future Agent Development Roadmap

1. **Add inventory-full verification after the withdraw plan**, before transitioning back to `goToAnvil` — e.g. a `SlotGate` on the last inventory slot (28) analogous to `indicatorSlot=26`'s empty-check, confirming the withdraw actually filled the inventory before smithing resumes. This directly closes the "1-click withdraw might under-withdraw" risk.
2. **Verify the bank's configured withdraw-quantity mode live** (in-game bank settings: 1/5/10/X/All) against the assumption baked into `withdrawSlot1Clicks=1`. If the bank isn't in "withdraw-all" mode, either set it once manually (simplest fix, no code change) or increase `withdrawSlot1Clicks`/extend the withdraw-plan pattern to click "withdraw-all" explicitly.
3. **Consider adding a `SlotSignatureGate`-style pre-check for multi-bar items** — if this bot is ever pointed at an item requiring more than 1 bar (platebody, etc.), the current `indicatorSlot`/`IsEmpty()` contract can hang until `phaseTimeoutAnvil` if leftover bars can't complete another full item. A pre-flight check (e.g. confirm bars-per-inventory divides evenly for the configured item) or a bar-count-aware variant of `PressAndWaitEmptyPhase` would remove this trap.
4. **Loosen `anvilMarkerTolerance`/`bankMarkerTolerance` from `0` to the shared `colorTolerance` value** (or a small nonzero value) if this bot is ever observed live re-clicking a marker without progress — that symptom (per ARCHITECTURE.md) means the color/size/position search is failing, and a `0` tolerance is the most fragile part of that search relative to every other calibrated value in this `.ini`.
5. **If multi-item-type smithing is ever wanted** (e.g. alternate between daggers and platebodies from the same bar stock in one session), this bot would need real item-selection-grid clicking added to a bot-specific replacement for `PressAndWaitEmptyPhase` — today it has zero interface navigation beyond the single space press, so it can only support "whatever the interface defaults to."
6. **If a second bar-type variant is wanted** (mirroring Smelter's `smelter-gold.ini`/`smelter-mithril.ini` pattern), duplicate `Config/auto-smithing-v2.ini` with a different withdraw-slot index/calibration and repoint `iniPath`, rather than adding branching logic to `smithing.ahk` itself — this matches the framework's established "same code, different `.ini`" pattern for per-item-type variants.
