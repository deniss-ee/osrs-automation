# Framework Reference — Helpers & Repeated Patterns

_Written 2026-07-09 after Motherlode; updated after Firemaking, Smelter, a cross-bot unification pass, `SlotSignatureGate`'s real implementation, and Smithing. Purpose: a lookup reference for building the next bot, so patterns are reused instead of reinvented._

## Layer map

```
Core/         Engine, EngineContext, FailSafe, Phase,
              SharedPhases                                  — state machine + shared context + timeout tripwire + reusable generic phases
Timing/       Waiter, TimingProfile                         — the only place Sleep() is called
Detection/    ColorSearch, TargetLock, Telemetry,
              StaticAnchor, DynamicTarget                   — finding things on screen
Actions/      Click, Humanizer, KeyAction                    — moving the mouse / clicking / pressing keys
Interfaces/   Inventory, Bank, Walk                          — bot-facing wrappers over Detection+Telemetry
Config/       Config                                         — typed .ini loading + schema validation
Diagnostics/  Logger, WindowFocus, Overlay                   — file log, focus guard, on-screen status
Bots/<Name>/  <name>.ahk                                     — entry point + bot-specific Phase classes
Config/       <name>.ini                                     — that bot's own config
```

Nine bots exist: **Motherlode** (7 phases, most complex — acquire/track mining loop, `TargetLock`-based stability, walking multi-tile course), **MotherlodeFixed** (3 phases — a structural rewrite of Motherlode for a stand-still setup with two always-visible fixed veins, not a bugfix; coexists with plain Motherlode rather than replacing it), **Firemaking** (4 phases), **Smelter** (4 phases, uses `SlotSignatureGate` — see below), **Smithing** (4 phases), **AutoFighter** (2 phases, both now shared — see dedicated section below), **AutoFighterLoot** (3 phases — AutoFighter's 2 shared phases plus a bot-specific `LootPickupPhase`), **FruitStall** (2 phases — a bot-specific `ThievingPhase` plus the shared `WaitCombatPhase`). Firemaking and Smithing share both generic phases from `Core/SharedPhases.ahk` (`PressAndWaitEmptyPhase` + `GoToBankPhase`); Smelter shares only `GoToBankPhase` (its "done" check needs `SlotSignatureGate`, not a plain empty-check — see Telemetry section); Motherlode/MotherlodeFixed's phases are all bot-specific since their acquire/track shape doesn't fit the generic pattern; AutoFighter/AutoFighterLoot/FruitStall share `ScanAndAttackPhase` and/or `WaitCombatPhase` (see dedicated section below) — no other bot scans the whole screen for irregular multi-target blobs or polls a raw combat-indicator pixel.

Every bot has its own `Bots/<Name>/README.md` covering its specific state machine, config reference, known risks/edge cases, and a future-development roadmap — this file stays the cross-bot reference; per-bot READMEs go deeper on that one bot's own logic and OSRS-mechanics-specific gaps.

Smelter has two `.ini` variants (`smelter-gold.ini`, `smelter-mithril.ini`) — same `smelter.ahk` code, different calibration/withdraw-plan values per metal. This is the pattern for "same bot, different game content": one code file, multiple `.ini`s, repoint `smelter.ahk`'s `iniPath` (or keep separate copies) per variant in use.

This framework was originally built alongside an older, legacy codebase kept as read-only reference material during development. That legacy code has since been removed from the repo entirely — this framework fully supersedes it. A few notes below still reference "legacy's" behavior as a historical attribution (explaining *why* something here is built the way it is, e.g. porting/superseding an older approach), not as a pointer to files that still exist in this repo.

## Core state machine

- **`Phase`** (base class): every phase has a `.name`; `Run(ctx)` returns the next phase's name. Returning the same name = "stay in this phase, tick again next cycle."
- **`Engine`**: owns `Map(name -> Phase)` + `Map(name -> timeoutMs)`. `Tick()` (on a `SetTimer`) is busy-guarded (`_busy` flag skips re-entrant ticks), checks `FailSafe.HasPhaseTimedOut()` before running, calls `phase.Run(ctx)`, and calls `ctx.failsafe.EnterPhase(...)` whenever the returned name differs from the current one. `AddPhase(phase, timeoutMs)` registers a phase with its per-phase timeout (0 = unlimited).
- **`EngineContext`**: the one state bag passed to every `Run(ctx)`. Holds `config`, `logger`, `clicker`, `failsafe`, `waiter`, `timing`, `windowFocus`, `overlay`, `inventory`, `bank`, `engine` (set post-construction so a phase can call `ctx.engine.Stop(reason)`), and a free-form `_state` Map for scratch values via `ctx.Get(key, default)` / `ctx.Set(key, value)`. `ctx.Log(text)` fans out to both `logger` and `overlay`.
- **`FailSafe`**: two independent tripwires — a per-phase timeout (reset via `ResetPhaseTimer(ctx)` on real progress, not every tick) and a consecutive-failure budget (`RecordFailure`/`RecordSuccess`/`HasExceededFailureBudget`, currently unused by Motherlode but available).

## Timing (the delay chokepoint)

- **Rule**: `Sleep()` is called in exactly one place in the entire framework — `Waiter.After(profile, key)`. No phase, no helper, ever calls `Sleep` directly.
- **`TimingProfile`**: `Map(key -> {baseMs, jitterPercent?})`, built by `Config.Load()` from a bot's `timingSchema`. `Has`/`BaseMs`/`JitterPercent`.
- **`Waiter.After(profile, key)`**: throws if the key isn't defined (no silent zero-delay fallback); applies an injected jitter function (`(baseMs, jitterPercent) => ms`, usually `Humanizer.Jitter`) then sleeps.
- **`Waiter.ForMs(ms)`**: explicit-duration escape hatch for library-level polling intervals that are a poll *rate*, not a bot-tunable action delay (e.g. `ImageAnchor.WaitFor`'s loop uses a named key via the caller, not this).
- **AHK v2 gotcha**: `this._someFn(a, b)` where `_someFn` holds a plain function (not a real method) is parsed as a method call, silently injecting `this` as a hidden extra arg → "Too many parameters" error. Fix: assign to a local first (`fn := this._someFn; fn(a, b)`).

## Detection primitives

- **`ColorSearch.FindFilledBlock(x1,y1,x2,y2,color,tol,reqW,reqH,&cx,&cy,scanBottomUp)`**: iterative (non-recursive, stack-based) search for a solid `reqW x reqH` block of `color`. Verifies via `VerifyBlock`'s 5-point cross-check (75% of requested size, anti-aliasing-safe). `scanBottomUp` reverses scan order for targets better found from the bottom edge (verification direction flips too). Returns the **verified block's own center**, clamped to the search region's bounds — not the full overlay blob's bounding-box center.
- **`ColorSearch.ColorClose(c1, c2, tol)`** / **`IsColorAt(x,y,color,tol)`**: per-channel RGB tolerance check; the primitive everything else is built from.
- **`TargetLock(stableTicksRequired, moveTolerancePx, missingTicksToUnlock=1)`**: stability debounce. `Observe(found,x,y,&outX,&outY)` always writes the latest real position when found (never freezes); `IsStable()` is a separate counter of consecutive in-tolerance ticks, used only to gate click cadence, never to stop tracking a drifting target. `IsLost()` flags "missing too long, re-acquire." `Reset()` clears both counters — call this whenever a phase (re-)acquires a fresh target, and on every per-cycle reset.
- **`StaticAnchor.ImageAnchor(region, imagePath, imageW, imageH, options)`**: `Find(&x,&y)` wraps `ImageSearch`, converting the returned top-left to a center point using caller-supplied width/height (AHK can't query a PNG's own size). `WaitFor(waiter, profile, pollKey, timeoutMs, &x, &y)` polls `Find` via `Waiter.After` between attempts, bounded by `timeoutMs`.
- **`StaticAnchor.FixedPointAnchor(x, y)`**: trivial anchor for a known/calibrated point clicked without any search — lets a phase treat "click a fixed coordinate" and "click wherever this image/color is" through the same `Find`/`WaitFor` contract.
- **`DynamicTarget.ColorBlockTarget(region, color, tolerance, reqW, reqH, lock)`**: wraps `ColorSearch.FindFilledBlock` + a `TargetLock` behind the same `Find(&x,&y)` contract, plus `IsStable()`/`IsLost()`/`Reset()`/`Retarget(region,color)`. Motherlode's phases currently inline this pattern by hand rather than using this class directly — worth using `ColorBlockTarget` directly in the next bot instead of re-inlining the acquire/track shape.
- **`NearestColorTarget`**: stub, picks the nearest of multiple matches to a reference point — not yet implemented (`_FindRawBlock` throws). Not used by AutoFighter — that bot needed the same *idea* (nearest match among several) but for irregular blobs rather than fixed solid blocks, so it got its own new primitives instead (below) rather than completing this stub.
- **`ColorSearch.FindNearestColor(x1,y1,x2,y2,refX,refY,color,tol,&nearX,&nearY,rowStep=4)`**: seed search for AutoFighter's targeting — finds the `color` pixel nearest to `(refX,refY)` within the region, checking one row per `rowStep` (not every row) and only the first match per checked row (not every match on that row). Both approximations exist for a hard performance reason: on the test machine, each individual `PixelSearch` call carries a large fixed per-call overhead (measured live at ~7ms/call) — a naive full-resolution scan of a 1440px-tall region took 2.5–30+ seconds depending on how many separate blobs were on screen. Coarsening the stride and taking only the first match per row cut a full-screen scan to ~400ms; scoping the region tightly around the reference point (AutoFighter's `targetSearchRadiusX/Y`) buys back a finer stride at similar total cost. **If a future bot needs this, budget total `PixelSearch` calls (region height ÷ rowStep) against this ~7ms/call figure before picking a stride, and prefer shrinking the search region over coarsening the stride** — a smaller region gets you both speed and precision, a coarser stride only gets you speed.
- **`ColorSearch.FindCentroid(x1,y1,x2,y2,color,tol,&cx,&cy,sampleRate=2)`**: average position of `color` pixels in a region, one sampled row per `sampleRate` rows (first match per row) — same performance shape as `FindNearestColor` above, and for the same reason (an earlier version used a brute-force per-pixel `PixelGetColor` loop; that alone caused a multi-second stall over even a small 120x120 box on this machine).
- **`ColorSearch.FindNearestBlobCenter(x1,y1,x2,y2,refX,refY,color,tol,blobRadius,&targetX,&targetY,sampleRate=2,seedRowStep=4)`**: the actual targeting primitive AutoFighter uses. Two steps: (1) `FindNearestColor` to seed on the nearest matching pixel to the reference point — this picks *which* blob is closest when several irregular, differently-shaped/sized overlays exist simultaneously (e.g. several NPCs in a pen); (2) `FindCentroid` on a `blobRadius`-sized box around that seed, clamped to the original region — the real click target, since the seed pixel itself likely lands on a blob's edge, not its middle. Ported from legacy's `FindNearestOutlineBlobCenter` (`lib/Targeting.ahk`) — legacy's own comments say this approach *supersedes* an older fixed-solid-block method (`FindNearestSolidColorBlockCenter`/`AcquireSolidColorBlockTarget`) for exactly this reason: `ColorSearch.FindFilledBlock` (the block method used by every other bot's fixed markers) requires a solid `reqW x reqH` rectangle and cannot handle an irregular, variably-shaped overlay — it will miss or mis-click on shapes like NPC outlines.

## Telemetry (boolean gates)

All expose `IsSet() => bool`, so a phase never cares which strategy backs a gate:
- **`SlotGate(slotIndex, tolerance, inventory, offsets?)`**: true if any of 4 sampled offsets inside the slot no longer matches `InventoryColors.EMPTY` (`0x3F3629`, measured once, session-invariant).
- **`NotGate(gate)`**: inverts.
- **`AndGate([gates])`**: true only if every wrapped gate is set — used for Motherlode's "truly full" check (slot 28 AND slot 27, since a lone gem in 28 isn't hoppered and shouldn't count as full).
- **`OrGate([gates])`**: true if any wrapped gate is set — used for "sack gave us something" (slot 2 OR slot 12, since a gem can land anywhere).
- **`SlotSignatureGate(slotIndex, tolerance, inventory, offsets?)`**: implemented (was a stub). `Calibrate()` snapshots the slot's sampled colors as a baseline — call this while the pre-transform item is visible (e.g. right after confirming a "smelt X" dialog, while ore still shows). `IsSet()` returns true once any sampled point differs from that baseline. **Why this exists over `SlotGate`/`NotGate`**: Smelter's ore→bar transform never empties the slot's background (a bar occupies the slot exactly like ore did), so `IsEmpty()` never fires — `SlotSignatureGate` detects "the item changed," not "the slot emptied." Smelter's `SmeltPhase` is bot-specific (not the shared `PressAndWaitEmptyPhase`) specifically because of this — see Shared generic phases section.
- **`PixelColorGate(x, y, tolerance)`**: not slot-anchored (no `Inventory` dependency) — checks a raw fixed screen point against an arbitrary color on demand via `Matches(color)`, rather than exposing a single `IsSet()`. Built for AutoFighter's combat-indicator pixel, which can be one of two meaningfully different colors (fighting vs. kill-confirmed) rather than a simple on/off state — `Matches(startColor)` / `Matches(killColor)` are both checked against the same gate instance.

**Gate composition pattern**: build individual `SlotGate`s, wrap in `AndGate`/`OrGate`/`NotGate` as needed, attach to `Inventory` via `SetFullGate`/`SetEmptyGate`/`SetSackGate`. This composition happens once at wiring time, in the bot's entry-point file, not inside phase logic.

## Actions

- **`Clicker.MoveTo(centerX,centerY,width=0,height=0,&targetX,&targetY)`**: applies `Humanizer.Offset` spatial jitter, moves the mouse, returns the actual target point via out-params (so a caller inserting a settle delay before `Press()` clicks the *same* point that was moved to — critical, since a delay-then-recompute pattern causes stale-coordinate clicks). No `Sleep`.
- **`Clicker.Press(button="Left")`**: fires the click at the current mouse position. Deliberately not named `Click` — a method sharing a name with an AHK builtin it calls internally resolves to self-recursion.
- **`Clicker.ClickAt(...)`** / **`ClickAtWithCtrl(...)`**: convenience wrappers with no settle delay — only for callers that genuinely don't need one.
- **`Clicker.ClickSettled(ctx, x, y, runMode=false)`**: the standard click every phase uses — `MoveTo` → `ctx.waiter.After(ctx.timing, "clickSettle")` → `Press()`, optionally wrapped in `Send("{Ctrl down/up}")` + `ctx.waiter.After(ctx.timing, "ctrlHoldSettle")` when `runMode` is on. This replaced 15 near-identical private `_Click(ctx,x,y)` methods that were hand-copied into every phase class across all 3 bots — call `ctx.clicker.ClickSettled(ctx, x, y, this._runMode)` directly instead of writing a per-phase wrapper. (Motherlode's `MinePhase` keeps a thin `_Click` wrapper only because it also applies a configured click offset before delegating to `ClickSettled`.)
- **`Humanizer(enabled, maxClickOffsetPx, maxDelayJitterMs)`**: pure policy object, no timing role. `Offset` returns bounded random spatial jitter (0,0 when disabled). `Jitter(baseMs, jitterPercent)` returns baseMs ± bounded/floored jitter — this is what gets injected into `Waiter`'s constructor as its jitter function. Currently constructed with `enabled=false` in all 3 bots (a deliberate no-op, kept as-is rather than removed — see Config section).
- **`KeyAction.Press(key)`**: `Send("{" key "}")` — used for one-shot key presses like `[space]` to confirm a dialog. No settle delay of its own; the caller wraps it in `ctx.waiter.After(...)` if one is needed (see `PressAndWaitEmptyPhase` below).

## Shared generic phases (`Core/SharedPhases.ahk`)

Two phase shapes turned out to be **byte-identical across bots apart from names/keys** — rather than copy-pasting a third/fourth time, they're generic classes any bot can construct directly:

- **`PressAndWaitEmptyPhase(name, keyAction, key, spaceSettleKey, nextPhaseName)`**: presses `key` once (with a settle delay), then polls `ctx.inventory.IsEmpty()` every tick with no further action until it's empty, then transitions to `nextPhaseName`. Used by Firemaking (`burnLogs`) and Smithing (`smith`) — same shape, different key/dialog/log context. Uses a shared `"keyPressed"` scratch flag (not `"spacePressed"` — the key isn't always space). **Not used by Smelter** — smelting doesn't empty the slot (ore→bar), so Smelter needs `SlotSignatureGate` instead (see Telemetry section); its `SmeltPhase` is bot-specific for exactly this reason. Before reusing this class for a new bot, confirm the crafted item actually *disappears* from the indicator slot rather than just changing appearance.
- **`GoToBankPhase(markerX, markerY, markerW, markerH, markerColor, markerTolerance, searchPaddingPx, reclickCooldownMs, markerWaitTimeoutMs, bankOpenAnchor, bankOpenWaitTimeoutMs, bankOpenPollKey, nextPhaseName, runMode=false)`**: verifies a fixed-point color marker, clicks it, waits for a bank-open image anchor, then transitions to `nextPhaseName`. Used by all of Firemaking/Smelter/Smithing (image is a pure "bank is open" signal for Firemaking, `nextPhaseName="withdrawLogs"`; the same image is then clicked as deposit-all by the *next* phase for Smelter/Smithing, `nextPhaseName="depositAndWithdraw"`) — the class itself doesn't care which; it only detects and hands off.

Both classes still require the caller to `#Include Core/SharedPhases.ahk` and construct them in the bot's own wiring section — they aren't auto-registered.

**Not (yet) unified, on purpose**: `GoToFirePhase`/`GoToFurnacePhase`/`GoToAnvilPhase` (structurally identical but scratch-key names like `"fireMarkerWaitStartedAt"` vs `"furnaceMarkerWaitStartedAt"` vs `"anvilMarkerWaitStartedAt"` are hardcoded per-bot — would need a prefix parameter threaded through every `ctx.Get`/`ctx.Set`) and the withdraw-plan polling/clicking loop (`WithdrawLogsPhase`/`DepositAndWithdrawPhase` in both Smelter and Smithing share the same loop shape, but Smelter's has an extra pre-step — a one-time deposit-all click — that plain Firemaking-style withdraw doesn't; Smithing's `DepositAndWithdrawPhase` *does* include that same deposit step, so it's actually closer to Smelter's shape than Firemaking's). Revisit if unifying starts saving more than it costs in indirection.

**A concrete miscalibration bug worth remembering**: Smithing's `.ini` initially had `bankMarkerColor=0xFF00FF` (magenta, copy-pasted from the anvil marker just above it) instead of the correct `0x0000FF` (blue) — `GoToBankPhase` silently re-clicked the bank marker forever without ever finding the wrong color, so it never reached the bank-open wait, and nothing ever got deposited/withdrawn. The log symptom was two "Clicked bank marker" lines exactly `reclickCooldownMs` apart with nothing after — that pattern (repeated re-clicks of the same marker, no further progress) means the color/size/position search is failing, even if the click itself is landing somewhere that happens to work in-game.

## AutoFighter / AutoFighterLoot / FruitStall (no bank/inventory step for combat itself)

AutoFighter (`Bots/AutoFighter/autofighter.ahk`) is architecturally different from the bank/inventory-cycle bots above: there's no fixed marker, no bank — just a whole-region scan for one of several simultaneous, irregularly-shaped NPC overlay blobs, and a raw combat-indicator pixel to know when a fight starts/ends.

**`ScanAndAttackPhase` and `WaitCombatPhase` now live in `Core/SharedPhases.ahk`, not in AutoFighter's own file** — they were promoted to generic shared phases once `Bots/AutoFighterLoot/autofighter-loot.ahk` needed the identical scan/click/wait-for-kill shape but with a different post-kill hand-off (a loot-pickup phase instead of looping straight back to scanning). `WaitCombatPhase` is now a *third* time reused by `Bots/FruitStall/fruitstall.ahk`, which has no attack click at all (passive aggro) — its 9th constructor arg, `retryNextPhaseName`, exists specifically for that bot (defaults to `killNextPhaseName` when omitted, which is why AutoFighter/AutoFighterLoot's own 8-arg call sites are unaffected). **Any future change to either class must be load-checked against all three consumer bots**, not just AutoFighter.

- **`ScanAndAttackPhase`**: scans a box around a calibrated reference point (`refPointX/Y` ± `targetSearchRadiusX/Y` — NOT the whole screen, see the `ColorSearch.FindNearestBlobCenter` perf note above) for the nearest matching color blob via `ColorSearch.FindNearestBlobCenter`, clicks its centroid, hands off to a configurable `nextPhaseName` (always `"waitCombat"` in practice). On repeated no-match, times out and stops the engine cleanly (same `xWaitStartedAt` + `ctx.engine.Stop(...)` pattern as every other bot). Used by AutoFighter and AutoFighterLoot; not used by FruitStall (which detects "an NPC is coming" via a loot-timeout instead of scanning for a blob).
- **`WaitCombatPhase`**: polls a `PixelColorGate` at a fixed indicator point for two colors — `combatStartColor` (fighting) and `combatKillColor` (kill confirmed). On a **fresh** kill, settles (`postKillSettleDelayMs`) and returns to `killNextPhaseName` (`"scanAndAttack"` for AutoFighter, `"lootPickup"` for AutoFighterLoot, `"thieving"` for FruitStall). If neither color appears within `retryClickAfterMs`, assumes the click missed (or, for FruitStall, that nothing has happened yet) and returns `retryNextPhaseName`, without waiting out the full `combatStartTimeoutMs` (which remains an outer ceiling in case retries keep failing). The phase timer (`ctx.failsafe.ResetPhaseTimer`) is reset unconditionally on **every** tick `startColor` still matches — not just once on the transition tick — so a long-but-genuinely-ongoing fight is never mistaken for a stalled phase and force-stopped by `phaseTimeoutCombat`. A `combatStartLogged` latch (independent of the retry-timeout tracking) ensures "Combat started" is logged exactly once per fight even when `startColor` is already showing on the very first tick this phase runs.

AutoFighterLoot (`Bots/AutoFighterLoot/autofighter-loot.ahk`) adds one bot-specific phase, `LootPickupPhase`: after a kill, right-clicks a dropped-item image anchor, clicks the resulting "take" menu option, then clicks inventory slot 1 — a 4-stage internal state machine under one phase name (mirrors Motherlode's `ReturnMine2Phase` staging pattern). Unlike this codebase's usual convention, a missed loot pickup does NOT stop the engine — it logs the miss and returns to `scanAndAttack` anyway, since losing one drop isn't fatal the way losing a bank marker is.

FruitStall (`Bots/FruitStall/fruitstall.ahk`) is the simplest of the three: a single bot-specific `ThievingPhase` (click a stall's ready-pixel, wait for inventory slot 1 to fill) that falls through to `WaitCombatPhase` on a loot-timeout instead of a missed attack — see that bot's own `Bots/FruitStall/README.md` for its specific risks (notably: no explicit "is slot 1 actually empty" check before trusting a fresh steal).

**Two gotchas specific to this bot, worth remembering for any future "poll a raw indicator pixel for a transient state" bot**:

1. **Stale-signal detection needs a real "was this already true at entry" baseline, not just "have we seen the *other* state yet."** The combat-kill-color indicator was measured live to linger on screen for ~3 seconds *after* a kill (death animation) — well past the bot's own settle delay. The first fix attempt required `combatStartColor` to be observed at least once before a kill counted as "fresh," but that broke **instant kills** (weak NPCs that die before the fighting color ever appears at all) — those got stuck waiting out `retryClickAfterMs` for a start signal that was never coming. The correct fix: snapshot whether the kill-color was *already* showing at the exact moment this phase was entered (right after a fresh click); only treat a kill-color reading as fresh once the indicator has been observed to leave that stale baseline value at least once (to background *or* to the start color) — not "must specifically see the start color first." This distinguishes "stale leftover from the previous kill" from "genuinely this fight's outcome" regardless of whether the fight had any visible ramp-up.
2. **A severe, non-obvious performance cliff**: on the development machine, each individual `PixelSearch`/`PixelGetColor` call carries a large, roughly-constant per-call overhead (~7ms), independent of the region size being searched *within* one call. A loop that calls `PixelSearch` once per row across a 1440px-tall region (a seemingly reasonable "scan every Nth row" approach) can cost seconds, not milliseconds, purely from call-count — this is not intuitive from reading the code, only from timing it live. Any future full-region scan should budget total call count against a similar per-call cost until proven otherwise on the target machine, and prefer shrinking the scanned region over relying on stride alone.

## Interfaces (bot-facing wrappers)

- **`Inventory(layout, fullGate?, emptyGate?, sackGate?)`**: `layout = {firstX, firstY, cols, rows, slotW, slotH, gapX, gapY}` measured from slot 1's **top-left corner** (not center) — keeps calibration numbers consistent. `SlotCenter(slotIndex, &x, &y)` does 1-based row-major index → screen center math. `IsFull()`/`IsEmpty()`/`HasSackItems()` just delegate to the attached gates — gates are attached post-construction via setters (`SetFullGate` etc.) to avoid a constructor cycle (gates need `SlotCenter`, which needs the `Inventory` to exist first). **Naming convention**: the local variable holding the gate passed to `SetFullGate` should be named `fullGate`, not `emptyGate` — this was a copy-paste naming bug in both Firemaking and Smelter (fixed) where the *full*-detecting gate was misleadingly named `emptyGate` because it's wrapped in `NotGate` for the empty check right below it. Motherlode named it correctly from the start.
- **`Bank(chestAnchor, depositAllAnchor, clicker, slotLayout="")`**: `OpenChest(&x,&y)` finds+clicks the chest/booth anchor; `DepositAll(waiter, profile, pollKey, timeoutMs)` waits for the deposit anchor then clicks it — **neither is used by any bot yet**; Firemaking/Smelter both click their bank markers/images directly via `ColorSearch`/`StaticAnchor` in their own phases instead, and construct a `Bank` solely for `WithdrawSlot`'s coordinate math. `WithdrawSlot(slotIndex, &x, &y)` is pure coordinate math (no click) given `slotLayout = {firstX, firstY, pitchX, slotW, slotH}` — deliberately doesn't click itself, since a proper settled click needs `ctx`/`waiter`, which `Bank` doesn't hold; the caller's own `ctx.clicker.ClickSettled(ctx, x, y, runMode)` does the actual clicking after calling this. `WithdrawPlan(plan)` is still a stub — both Firemaking's `WithdrawLogsPhase` and Smelter's `DepositAndWithdrawPhase` inline their own `{slotIndex, clicks}` polling loop instead (see below) rather than complete/use this stub.
- **Withdraw-plan pattern** (not a `Bank` method, but a repeated shape): a bot's `.ini` declares `withdrawSlotCount=N` plus `withdrawSlot<i>Index`/`withdrawSlot<i>Clicks` for `i` in `1..N`; the wiring section builds an ordered array via `loop botConfig.Get("withdrawSlotCount") { ... }`; the withdraw phase steps through the array with `withdrawPlanIndex`/`withdrawClicksDone` scratch state, calling `Bank.WithdrawSlot` + `ClickSettled` per click, gated by a `withdrawClickIntervalMs` cooldown between repeats on the same slot. Firemaking uses a trivial 1-slot/1-click plan; Smelter uses a 2-slot plan (4 clicks then 1 click) — same shape, just more entries.
- **`Walk(waypoints, clicker)`** / **`Waypoint(clickX, clickY, arrivalAnchor)`**: generalizes the returnMine1/returnMine2 hand-rolled-stage-integer pattern into an ordered waypoint list — `ClickCurrent()` clicks the active waypoint, `CheckArrival(&x,&y)` checks its anchor and auto-advances, `IsComplete()` when all waypoints are done. **Motherlode's `ReturnMine1Phase`/`ReturnMine2Phase` still do NOT use this class** — still hand-rolling `ctx.Get("return2Stage", 1)`. Deliberately left alone (working, live-verified code; not worth the risk of touching for a pure-refactor pass) but still the right tool if a future bot needs multi-waypoint traversal.

## Config

- **`Config(iniPath, schema, timingSchema)`**: `schema` = `Map(key -> {section, type})` for plain values (`"int"|"float"|"color"|"str"`); `timingSchema` = `Map(timingKey -> {section, baseMsKey, jitterPercentKey?})` for `Waiter`-consumed delays. `Load()` reads every declared key **once**, collects **all** missing keys before throwing (one error listing everything, not one-at-a-time), and builds `this.timing` (a `TimingProfile`) as a side effect. `Get(key)` reads a plain value.
- **Absolute rule**: every pause/delay/coordinate/color/threshold is `.ini`-backed; nothing hardcoded in phase code. The one sanctioned exception is `Inventory`'s pixel-grid layout (`firstX/firstY/cols/rows/slotW/slotH/gapX/gapY`) — a fixed property of one client window, not a gameplay tunable, so it's a hardcoded `Map` in the bot's entry-point file rather than an `.ini` key (matches legacy's own treatment of `Grid.ahk` constants). All 3 bots currently use the identical inventory layout values (same client window).
- **Per-bot `.ini` duplication, kept intentionally**: `clickSettleMs`, `clickSettleJitterPercent`, `ctrlHoldSettleMs`, and (for bots with a withdraw plan) `withdrawClickIntervalMs` are copy-pasted identically across all 3 `.ini` files rather than centralized in a shared config file. Confirmed as a deliberate choice — no shared-config-loading mechanism exists yet (`Config` always loads exactly one bot's own `.ini`); building one was considered and explicitly deferred as unnecessary complexity for 3 bots. Keep these values consistent by convention when hand-editing, since there's no structural enforcement.
- **Humanization/jitter plumbing is fully inert but intentionally still present**: `Humanizer` is constructed with `enabled=false` in every bot, so `Offset`/`Jitter` are no-ops (return 0,0 / `baseMs` unchanged respectively) — `clickSettleJitterPercent` in every `.ini` currently does nothing. This was a deliberate choice, not an oversight: the user considered removing the mechanism entirely and chose to leave it in place rather than risk destabilizing working code for a cosmetic cleanup. Don't add *new* jitter-related keys to future bots, but don't strip the existing ones either without being asked.

## Diagnostics

- **`Logger`**: file-backed log (`logs/<bot>-debug.log`), one file per bot.
- **`WindowFocus(winTitle="ahk_exe RuneLite.exe")`**: `IsActive()` guards every phase's `Run` — `if ctx.windowFocus != "" && !ctx.windowFocus.IsActive(): return <same phase name>`, so a lost-focus window never fires a click. Repeated as the very first check in every Motherlode phase's `Run(ctx)`.
- **`Overlay(maxLines, x, y)`**: rolling on-screen `ToolTip` log of the last N lines — purely cosmetic/diagnostic, fed by `ctx.Log`.

## Repeated phase-authoring patterns (the actual "helpers" to reuse)

1. **Window-focus guard**: first line of every `Run(ctx)`.
   ```
   if (ctx.windowFocus != "" && !ctx.windowFocus.IsActive())
       return this.name
   ```
2. **Acquire/Track two-mode shape** (`MinePhase`, `ClearRedPhase`, `ClearYellowPhase`): a phase-local `ctx.Get("<x>HasTarget", false)` flag branches between `_Acquire(ctx)` (full-region search, locks a target + resets `TargetLock` on success) and `_Track(ctx)` (narrowed re-search around last known position, feeds `TargetLock.Observe`, clicks only per stability + cooldown rules). Losing the target resets the flag back to acquire mode.
3. **One-time settle delay via a scratch flag**: `if (!ctx.Get("xDelayApplied", false)) { ctx.waiter.After(...); ctx.Set("xDelayApplied", true) }` — used everywhere a phase needs to wait once upon first entering a state, not every tick. This is the fix pattern for the recurring "instant click right after a fresh detection" bug class that showed up four separate times this session.
4. **Delay-before-search, not delay-after-search-before-click**: when a settle delay and a coordinate search both need to happen, the delay must come first — searching, then sleeping, then clicking stale pre-sleep coordinates was the root cause of the `DepositBankPhase` stale-click bug.
5. **Non-blocking cooldown check**: `if ((A_TickCount - lastClickTime) > cooldownMs) { click; lastClickTime := A_TickCount }` — never a blocking `Sleep` for cadence, always a tick-driven timestamp comparison.
6. **Bounded indefinite wait with a `ctx.engine.Stop(...)` failsafe**: track a `xWaitStartedAt` timestamp on first entry, compare against a configured timeout every tick, log + `ctx.engine.Stop(reason)` (never throw, never loop forever) if exceeded.
7. **`ResetForNewCycle()` per phase + a shared `nextCyclePhases` array**: every phase that holds cross-cycle state (a `TargetLock`, or scratch timestamps not already covered by the two central reset points) implements `ResetForNewCycle()`. Two places call it on every phase in the shared array: the inventory-full transition in the "start of loop" phase, and the final phase's completion (which also resets literally all scratch state and hands off back to the loop's start). This is the mechanism that makes a second full cycle behave identically to the first.
8. **Settled clicks via `Clicker.ClickSettled(ctx, x, y, runMode)`**: no longer a per-phase private helper — call it directly. See Actions section above. (This used to be a hand-copied `_Click(ctx,x,y)` method in all 15 phase classes across all 3 bots; unified in the cross-bot cleanup pass.)
9. **Engine wiring order**: downstream phases must be constructed *before* an upstream phase whose constructor needs to receive them (e.g. `MinePhase` needs the full `nextCyclePhases` array, so every other phase is built first and pushed into that array incrementally).
10. **Per-phase-group timeout keys**: don't share one `phaseTimeoutX` across phase groups whose internal wait-failsafes have materially different magnitudes — the engine's generic phase timeout can race ahead of and mask a phase's own more specific internal timeout message. Motherlode uses four separate timeout keys (`phaseTimeoutMine`, `phaseTimeoutBank`, `phaseTimeoutSack`, `phaseTimeoutReturn`); Firemaking/Smelter each use two (`phaseTimeoutFire`/`phaseTimeoutFurnace` + `phaseTimeoutBank`).
